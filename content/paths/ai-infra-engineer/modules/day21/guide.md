# Day 21 · 规模化调度问题深化

> 目标：拓扑感知/亲和性/碎片化——千卡集群的调度器视角

## Day 4 问题的千卡版

Day 4 讲过「8 个小 Pod 各占 1 卡，大任务凑不齐整机」。千卡集群的调度问题升级成三个：

## ① 拓扑感知——调度对了位置，NCCL 快一倍

GPU 在机器里有层级：**NVLink 域（同机 8 卡全互联）→ PCIe/NUMA 域 → 机器**。同一个 8 卡任务：

- 调度到**同机 8 卡（NVLink 全互联）**：Ring-AllReduce 走 NVLink（300-900 GB/s）
- 被散到**两台机器各 4 卡**：跨机部分走 IB（≤50 GB/s），且多一跳网络

**同一份代码、同一个模型，性能差 2-5 倍——纯调度位置决定**。这就是拓扑感知调度（topology-aware scheduling）的价值：调度器要「懂」NVLink 拓扑（NVIDIA GPU Operator 的 node label / topology manager 就是干这个）。

**运维检查法**：任务起来后 `nvidia-smi topo -m` 看实际分到的卡在哪个域；`NCCL_DEBUG=INFO` 的 topo 初始化日志——**你的调度器没用拓扑感知，大任务性能天然打七折**。

## ② 碎片化的量化——不度量就无法治理

```
碎片率 = 1 - 最大可分配整机数×整机卡数 / 空闲总卡数
例：空闲 200 卡，但最多凑齐 4 台整机（32 卡）→ 碎片率 = 1-32/200 = 84%
```

200 张「空闲」卡里 168 张是**逻辑上不可用的**（散在小任务上）。Day 19 的「gang 等待成本」其根源就是这。治理手段：整机池 vs 共享池分离（大任务专用整机池）、定期重排（descheduler）、任务装箱策略。

## ③ 装箱策略的「训练反转」

Web 服务调度习惯** spreading**（副本尽量分散到多机——容灾）。训练任务**反转**：要 **binpacking**（装箱紧凑）——因为：
- 同任务的多卡要**近**（拓扑！跨机通信慢）
- 空出的整机是完整资源（下一个大任务能立刻用）

**这就是老运维知识需要显式修正的地方**：你肌肉记忆里的「分散=好」在训练调度上是错的。

## 打分器扩展（平台工程视角）

Volcano/gpu-manager 的调度打分 = 亲和性 + 拓扑代价 + 碎片代价的加权和。平台团队真正写的代码是**这些打分项**——「怎么算一张卡对某个任务的分」。面试聊到这层，你就是「设计过调度器扩展」的人而非「用过 Volcano」的人。
