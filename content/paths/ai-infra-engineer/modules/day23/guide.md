# Day 23 · 故障注入与演练体系

> 目标：从「救火」到「演习」——把 GPU 故障变成可预案可训练的常规事件

## 为什么演练比救火更重要

Day 15 的数据（54 天 419 次故障）意味着**万卡集群每天挂 8 次**——靠「故障了再查」的模式，运维团队天天在救火。成熟平台的做法是**主动注入故障**：在业务低峰把 XID/ECC/断网/杀进程演一遍，度量「发现→定位→恢复」的时长（MTTR），把预案练成肌肉记忆。

## XID 速查表（背 5 个高频的）

| XID | 含义 | 处置 |
|-----|------|------|
| **79** | GPU 掉了（驱动/链路层） | 摘节点、看 dmesg |
| **48** | ECC 不可纠错（双比特） | **硬件实坏**——下线送修 |
| **63/64** | 显存 ECC 可纠错/污染 | 观察 SBE 增速，快速涨=要坏 |
| **13** | 显存引擎错误 | 常伴随其他 XID，看上下文 |
| **31** | GPU 内存页错误 | 多为应用 bug，先看进程 |

**运维纪律**：`nvidia-smi -q` 的 ECC 计数要**入库监控**（SBE 持续增长是「要坏」的前兆指标——提前 2 周下线好过半夜炸）。

## 故障注入的两级方法

**软注入（无风险，先练这级）**：
```bash
kill -9 <训练进程>            # 模拟节点级崩溃 → 验证 K8s 重建+续训恢复
ip link set <网卡> down/up    # 模拟网络抖动 → 验证 NCCL 超时与任务表现
```

**硬注入（有风险，小范围灰度做）**：
- 拔某节点的 IB 线 / 重启交换机端口（约好窗口）
- `nvidia-smi -r` 重置 GPU（模拟掉卡）
- DCGM 有 `dcgmi inject`（诊断注入模式）——部分场景可模拟错误

## 演练的设计（一次完整摘卡演练）

```
① 目标：验证 64 卡任务遇 1 节点 XID79 的 MTTR
② 注入：低峰期对任务的第 3 个节点 kill 进程（软注入）
③ 度量：故障发现时长（告警到人）｜定位时长（找到坏节点）｜恢复时长（续训完成）
④ 验收：loss 从断点连续、总 MTTR < 15 分钟
⑤ 复盘：哪一步靠人肉（该自动化的）、runbook 哪条写错了
```

**runbook 最小结构**（四行就够，别写成文档工程）：症状（怎么发现的）→ 判断（3 条内定位路径）→ 处置（命令级）→ 升级（什么时候叫谁）。

**演练频率**：新平台每月 1 次关键场景；稳定后季度 1 次 + 大变更（网络改造/驱动升级）后加演。**MTTR 是演练的北极星**——真实故障的恢复表现几乎等于最近一次演练的表现。
