# Day 15 · Checkpoint 与容错

> 目标：断点续训——万卡集群 54 天 419 次故障的现实

## 为什么这是训练运维的灵魂课题

Meta 的 Llama-3 训练报告：**54 天里 419 次意外中断**——平均每 3 小时一次故障（GPU 硬件 58%、网络 11%、宿主机 9%…）。万卡集群的容错不是「会不会坏」而是「坏了怎么最快恢复」。**没有 checkpoint 策略的训练平台，等于把 GPU 时薪押注在硬件永不故障上**。

## checkpoint 的三要素（少一个都续不上）

| 要素 | 内容 | 缺了会怎样 |
|------|------|-----------|
| 模型权重 | state_dict | 前功尽弃 |
| **优化器状态** | Adam 的一二阶动量（**模型大小的 2 倍体积！**） | 续训 loss 跳变、前几百步等于白训 |
| **数据/步数位置** | consumed_samples、epoch、sampler 状态 | 数据从头喂/重复喂，训练分布被污染 |

**运维关键认知**：一个 70B 模型的完整 checkpoint ≈ 70×（2 权重 + 8 优化器）≈ **700GB**——这就是为什么 checkpoint 的存储吞吐与分层设计是平台级问题。

## 恢复流程（标准五步）

```bash
# 1. 找最新可用 checkpoint（注意：最后一个可能是坏的——保存中途挂了）
#    平台侧应保留最近 N 份 + 异步校验完整性
# 2. 排除故障节点（XID/ECC 确认后摘除，弹性场景 world_size 减一）
# 3. 从存储拉 checkpoint 到本地 NVMe（700GB 走 25GB/s IB ≈ 28s）
# 4. torchrun 加 --rdzv 恢复，训练代码 load + 恢复 sampler 位置
# 5. 验证：续训前 10 步 loss 与中断前连续（跳变=优化器状态没存对）
```

## 保存频率的权衡（必会算的账）

- 保存太频：每次 700GB×分钟级 IO——训练吞吐被 checkpoint 吃掉
- 保存太稀：一次故障丢 N 步——GPU 时薪 × N × 单价
- **平衡公式**：保存间隔 ≈ sqrt(单次保存耗时 × 故障成本系数)；实践中常见 **每 1000-5000 步**，配合异步保存

**异步/分层保存**（大厂标配）：
```
显存 → (CPU 内存暂存, 训练不阻塞) → 本地 NVMe → (后台) 对象存储
```
同步保存会把训练打断分钟级；分层异步把阻塞压到秒级。

## 面试高频题速答

- 「优化器状态为什么必须存？」→ Adam 动量是历史梯度统计，丢了等于冷启动，loss 跳变几百步
- 「checkpoint 为什么不能只留最新一份？」→ 最后一份可能恰好在保存中损坏；保留 N 份 + 完整性校验
- 「弹性容错（节点摘除后续训）难在哪？」→ world_size 变化要求框架重塑（TP/PP 分组重算）、sampler 重新切分——Megatron/Skywork 式 elastic 训练是专门能力
