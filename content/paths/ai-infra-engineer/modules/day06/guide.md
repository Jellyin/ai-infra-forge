# Day 6 · 量化、并行、长上下文

## 6.1 量化：用精度换显存和速度

**本质**：把权重/激活的数值精度从 FP16 降到 FP8/INT4，减少显存和计算量。

| 精度 | 字节/参数 | 显存(70B) | 精度损失 | 现状 |
|------|-----------|-----------|---------|------|
| FP16/BF16 | 2 | 140GB | 无 | 默认 |
| FP8 | 1 | 70GB | 极小 | **H100+ 原生支持，生产主流** |
| INT8 | 1 | 70GB | 小 | 激活量化，部署多 |
| INT4(GPTQ/AWQ) | 0.5 | 35GB | 中等 | 显存紧张/大模型压小卡 |

**面试答案**：量化是「精度」和「显存/吞吐」的权衡。MaaS 平台通常提供 FP8 和 INT4 两档给用户选：FP8 保精度，INT4 省显存。

**动手**：用 `--quantization` 参数起两个量化版本，对比显存占用和输出质量：

```bash
# FP8（需要 H100/Ada 以上）
vllm serve Qwen/Qwen2.5-7B-Instruct --quantization fp8

# INT4（AWQ 权重，需要先下载 AWQ 版本）
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ --quantization awq
```

## 6.2 并行策略：模型太大单卡装不下

| 策略 | 怎么切 | 通信 | 适用 |
|------|--------|------|------|
| TP（张量并行） | 一层内切分到多卡 | NVLink 高频 | **单机内首选** |
| PP（流水线并行） | 按层切分 | 低频但利用率低 | 跨机 |
| DP（数据并行） | 多副本各自服务请求 | 无 | **水平扩容的本质** |

**对应参数**：`--tensor-parallel-size 4`、`--pipeline-parallel-size 2`。

**决策逻辑（面试题「70B 两卡怎么部署」的完整答案）**：
1. 70B FP16 = 140GB，两卡 160GB 装得下权重但只剩 20GB 给 KV Cache，几乎无法并发。
2. 正确做法：**FP8 + TP=2**（每卡 35GB，余量充足），或 **INT4 单卡/两卡**（35GB 总，最省）。
3. 别忘了算 KV Cache 的额外需求。

## 6.3 长上下文与 2026 前沿（面试加分项）

### 长上下文（1M token）

1M token 上下文的 KV Cache 是几百 GB，根本放不下，所以方向是：
- **KV Cache 压缩**：MLA（DeepSeek 用的 Multi-head Latent Attention）、量化 KV Cache。
- **稀疏注意力**：不是所有 token 都互相注意。

### Prefill/Decode 分离（Disaggregation）

**当前头部推理平台的重点演进方向**：把 Prefill（吃算力）和 Decode（吃带宽）拆到不同 GPU 池，各自选最合适的硬件、各自独立伸缩。能聊这个说明你紧跟前沿。

### Speculative Decoding（投机采样）

小模型「草稿」快速生成 + 大模型「验证」纠正，加速 decode。用「草稿模型的低成本」换「大模型的验证速度」。

### MoE 模型（DeepSeek 类）

参数总量大（671B）但**每次只激活一小部分专家**（37B）。调度和显存管理不同：全量参数要放显存，但计算量只按激活参数算。
