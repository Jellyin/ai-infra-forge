# Day 24 · 多模态推理运维

> 目标：VLM 的显存特征与部署差异——视觉编码器是另一头显存大户

## VLM 的双塔结构（运维视角的三个新对象）

```
输入图像 → [ViT 视觉编码器] → 视觉 token 序列 → [LLM 主干] → 输出文本
              ↑ 显存大户 ①             ↑ 膨胀点 ②          ↑ 你熟悉的部分
```

- **ViT 权重**（~1-2GB 级）：不大但独立存在——它是第二个「模型」
- **视觉 token 的 KV Cache**：一张高清图 = 数百上千个视觉 token，**每个都占 KV**
- **图像预处理**（resize/patch 化）：CPU 开销大——多模态服务的 CPU 配比要比纯 LLM 高

## 显存账的新公式（在 Day 3 基础上扩展）

```
VLM 总显存 = LLM 权重 + ViT 权重 + KV Cache(LLM token + 视觉 token) + 激活
视觉 token 数 ≈ (图像分辨率 / patch² )，典型 patch=14/16
例：1024×1024 图，patch=16 → 64×64 = 4096 视觉 token ≈ 4K 文本的 KV 占用
```

**容量规划直觉**：图片请求 ≈ 等效于「带 4K 附加 prompt 的文本请求」——但用户对**传图大小没概念**（4K 分辨率照片 ≈ 16K token 等效）。**入口必须限制图像分辨率/压缩**，否则几张原图就能打爆 KV 池——这是多模态网关比 LLM 网关多出的一条红线。

## 吞吐特征差异（容量模型要重学）

- **TTFT 构成变了**：图像编码（ViT 前向）+ prefill——**图像越大 TTFT 越长**，且这段是纯算力（不可流式）
- **批处理收益更高**：图像编码可独立 batching（ViT 无自回归依赖）——多模态的 continuous batching 收益比纯 LLM 更明显
- **输出短**：图片问答的生成 token 通常远少于长文任务——**decode 占比低，瓶颈前移到 prefill/编码**

## 部署参数差异速查

| 参数 | 纯 LLM | VLM 增量 |
|------|--------|---------|
| max-model-len | 8-32K | 需含视觉 token（再加 2-8K） |
| 并发估算 | 按 token | 按「图×等效 token」 |
| CPU 配比 | 常规 | **调高**（预处理） |
| 网关限制 | 输入长度 | **+图像分辨率/张数硬限** |

**面试答法**：VLM 运维的本质是「**KV 预算要按图像等效 token 计价 + prefill 成为新瓶颈 + 入口要有图像闸门**」——把 Day 1-8 的推理知识平移过来，多出这三条。

**今日作业**：算一道容量题——VLM 服务（8K 上下文 + 单图 1024² ≈ 4K 视觉 token），KV 池 20GB、每 token KV 0.5MB，能撑多少并发？（答案：单请求 12K token × 0.5MB = 6GB → **约 3 并发**——多模态的容量比你直觉的小得多）
