# Day 1 · 大模型推理基础

## 1.1 为什么「会运维」不等于「会运维大模型」

传统 Web 服务的心智模型是：

```
请求 → 网关 → 无状态应用(CPU) → 数据库 → 返回
```

大模型推理的心智模型是：

```
请求 → 网关 → 推理引擎(占满GPU显存) → 流式返回 token
```

三处根本差异，是整个岗位的认知地基：

**差异一：资源瓶颈从 CPU 变成显存**
- 传统服务加 CPU、加内存就能扩容；LLM 推理的硬约束是 **GPU 显存（HBM）**。
- 一个 70B 模型 FP16 权重就要 140GB，两块 80G 的卡都装不下。显存不够，服务直接起不来，不是「慢」而是「无」。
- 所以「显存水位」成了比「CPU 利用率」更关键的指标。

**差异二：从无状态变成有状态**
- 传统服务无状态，随便水平扩容。
- LLM 推理过程中要维护 **KV Cache**（后面详讲），它按 token 数线性增长。序列越长、并发越高，显存占用越大。这决定了「并发上限由显存决定」。
- 状态也让「优雅缩容」变难——正在推理的请求不能随便杀。

**差异三：从一次性响应变成流式输出**
- 传统服务：一次请求 → 一次 JSON 响应。
- LLM：逐 token 生成，通过 **SSE（Server-Sent Events）** 一行一行推给用户。
- 带来的指标变化：不是「响应时间」，而是 **TTFT（首字延迟）+ TPOT（每字延迟）**。

## 1.2 必须吃透的 5 个核心概念

### ① Transformer 推理的两个阶段

大模型（GPT/Qwen/Llama 类）基于 Transformer 架构。一次完整推理分两段：

```
[Prefill 预填充]           [Decode 生成]
输入 prompt 一次性并行处理  →  逐 token 自回归生成
计算密集（吃算力 FLOPS）     显存带宽密集（吃 HBM 带宽）
算得快但需要一次投入          每个 token 都要读 KV Cache
```

- **Prefill**：把用户输入的所有 token 一次性过一遍网络，产生第一个输出 token。因为是并行计算，**吃的是 GPU 算力（计算密集）**。
- **Decode**：从第二个 token 开始，每次只生成一个，且每一步都要读取之前所有 token 的 KV Cache。**吃的是显存带宽（内存密集）**。

**这个区分的意义**：优化方向完全不同。Prefill 慢 → 提升算力 / 分块处理；Decode 慢 → 优化 KV Cache 访问 / 投机采样。面试一定会问。

### ② KV Cache

推理时，每个 token 会计算出 Key 和 Value 向量。Decode 阶段每生成一个新 token，都要和之前所有 token 做「注意力」运算。如果不缓存，每个新 token 都要重新计算之前所有 token 的 K/V——计算量会平方级爆炸。

**KV Cache 就是把这些 K/V 存起来复用**。代价是占显存：

```
KV Cache 显存 ≈ 2 × 层数 × KV头数 × 头维度 × 精度字节数 × 序列长度 × 批大小
```

一句话：**KV Cache 决定显存占用和并发上限，序列越长占越多**。这是整个 MaaS 平台最核心的资源变量。

### ③ TTFT 与 TPOT

| 指标 | 全称 | 含义 | 用户体感 |
|------|------|------|---------|
| TTFT | Time To First Token | 发请求到收到第一个 token 的时间 | 「快不快」 |
| TPOT | Time Per Output Token | 后续每个 token 的间隔 | 「整体多久出完」 |

- 流式场景（Chat）最看重 **TTFT**——用户看到第一个字的速度。
- 批量场景（文档处理、批生成）最看重 **tokens/s 总吞吐**。
- 一个请求总耗时 ≈ TTFT + TPOT × 生成 token 数。

### ④ Continuous Batching（连续批处理）

传统推理引擎（老 Triton）是 **静态 batching**：攒一批请求，一起算，等最慢的那个算完才一起返回。问题是：一个请求 10 个 token，另一个 1000 个 token，短的那个要陪着长的干等，GPU 空闲浪费。

**连续批处理**：请求**随时来随时加入当前正在算的 batch，谁算完谁退出**，位置立刻让给排队的请求。GPU 几乎不空转。

- 这是 vLLM 碾压老引擎的核心，也是「为什么 vLLM 快」的标准答案。

### ⑤ PagedAttention（分页注意力）

KV Cache 如果按「每个请求一段连续显存」分配，会像 C 语言 `malloc` 一样产生**外部碎片**——碎片加起来够用但连不起来，导致显存利用率只有 ~50%。

**PagedAttention 把 KV Cache 切成固定大小的 block（页），像操作系统虚拟内存分页一样管理**，块与块之间不必连续。碎片消失，显存利用率提到 ~90%。

- 这也让「前缀缓存」成为可能——多请求共享相同前缀时，共用同一批 block。

## 1.3 面试考点速记

- 说出大模型推理 vs 传统服务的三点本质差异（资源/状态/响应模式）。
- Prefill 吃算力、Decode 吃带宽，优化方向不同。
- KV Cache 决定显存和并发上限。
- TTFT 管体验，tokens/s 管成本。
- Continuous Batching 解决「GPU 空等」，PagedAttention 解决「显存碎片」。
