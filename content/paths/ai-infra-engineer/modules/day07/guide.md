# Day 7 · 高并发网关与流量治理（你的主场）

## 7.1 传统网关知识完全复用 + 三个新挑战

你在限流、熔断、降级、负载均衡上的能力**全部能复用**。但要叠加三个 LLM 特有的挑战：

**挑战一：流式协议（SSE / gRPC streaming）**
- 响应是长连接逐 token 推送，不是一次性返回。
- 网关必须：关闭 response 缓冲、设置超长的读写超时（推理可能几十秒到几分钟）、支持连接复用。

**挑战二：并发上限由显存决定，不是 CPU**
- 限流要限「并发数」，不是简单的 QPS。
- 显存打满 = 服务不可用，和 CPU 打满不同（CPU 打满只是慢，显存打满直接 OOM 崩）。

**挑战三：按模型/租户路由**
- 一个平台有多个模型、多个版本、多租户，网关要按「模型名」路由到对应后端池。

## 7.2 网关要做的事

| 能力 | 说明 | 工具 |
|------|------|------|
| 限流 | 令牌桶 + **并发数限制** | APISIX/Envoy/Kong 都有 |
| 负载均衡 | least-conn 优先（推理耗时不均） | 同上 |
| 排队与背压 | 队列过长返回 429 或排队号 | 自研或网关插件 |
| 熔断降级 | 过载熔断，或降级到小模型 | 网关熔断 + 双模型池 |
| **语义缓存** | 相似问题直接返回缓存，白省 GPU | Redis + 向量相似度 |
| A/B 灰度 | 按模型版本/用户分流 | 网关路由 |

## 7.3 动手：APISIX 网关配置（完整可用）

```bash
# 1. 起 APISIX
docker run -d --name apisix -p 9080:9080 -p 9180:9180 \
  -e APISIX_STAND_ALONE=true apache/apisix

# 2. 配置一个 route 指向 vLLM（关键在 timeout 和 SSE 透传）
curl http://127.0.0.1:9180/apisix/admin/routes/1 -X PUT -d '
{
  "uri": "/v1/*",
  "upstream": {
    "type": "roundrobin",
    "nodes": { "127.0.0.1:8000": 1 }
  },
  "timeout": {
    "connect": 6,
    "send": 300,
    "read": 300
  },
  "plugins": {
    "limit-conn": { "conn": 64, "burst": 16, "default_conn_delay": 1 }
  }
}'
```

**关键配置解读**：
- `timeout.read: 300`：读超时设 300 秒，否则慢推理（长文本生成）会被默认 60s 掐断——这是 LLM 网关最常见的坑。
- `limit-conn`：**并发数限制**（而非纯 QPS），因为显存决定并发上限。

**必须手动验证**：
1. `curl -N` 经过网关后仍能流式逐 token 输出（SSE 透传没被缓冲）。
2. 并发超过 64 时返回 429（限流生效）。
3. 一个长文本生成请求不被超时掐断。

## 7.4 语义缓存（Semantic Cache）

**这是 LLM 平台独有的高并发优化手段，面试要重点讲**：

传统缓存是「精确匹配 key」，LLM 的语义缓存是「**语义相似**就命中」。做法：把用户问题向量化，在向量库里找最相似的已缓存问答，相似度超阈值直接返回缓存结果。

- 收益：高频相似问题（如客服、知识库问答）可省 50%+ GPU 算力。
- 代价：可能返回「不够精确」的答案，需要阈值权衡。
- 技术栈：Redis + 向量索引（如 RedisVL、Milvus）。
