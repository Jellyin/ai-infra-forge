# Day 17 · 微调工程化

> 目标：LoRA/QLoRA——SFT 全链路与发布衔接

## 微调的三条路线（按成本排）

| 路线 | 训练参数 | 显存（7B） | 适合 |
|------|---------|-----------|------|
| 全参微调 | 100% | ~80GB | 效果天花板，预算充足 |
| **LoRA** | <1% | ~20GB | **默认选择**：效果接近全参 |
| QLoRA | <1% | **~8GB** | 4bit 量化底座 + LoRA——消费卡可跑 |

QLoRA 的魔法 = 把冻结的底座量化成 4bit（NF4）省显存，可训的 LoRA 旁路保持高精度。**面试点**：QLoRA 训练时量化、推理时可合并回 FP16（或保持 4bit 部署）。

## SFT 全链路（这是「工程化」的本体）

```
① 数据准备（指令对→清洗→去重→格式化 chat template）
② 训练（LoRA + 有效 batch + lr 调度）
③ 评测（held-out 集 + 业务指标，不是只看 train loss）
④ 合并导出（merge adapter → 部署格式）
⑤ 发布（灰度→对照→全量——衔接 Day 7-8 的推理侧）
```

**运维最容易踩的坑在 ③**：train loss 降≠效果好——**没有评测集的微调是盲调**。工程红线：每次微调必须带 held-out 评测（loss + 至少一个业务指标），否则不给进 ④ 发布。

## 微调与推理的衔接（你的平台视角）

- 训完的 adapter（20MB）与底座（14GB）**分离存储**——底座共享、adapter 按版本管理
- 服务侧**热加载 adapter**：一个 vLLM 副本底座不动，按路由加载不同任务的 LoRA（多租户利器）
- 发布走你熟悉的灰度：新旧 adapter 同时在线，按流量切分对照——**微调的发布和 Web 服务发布同构**，这是运维经验的直接折算

## 常见微调失败模式（排障清单）

1. loss 不降：lr 不对（LoRA 要 1e-4 量级）/ 数据格式错（chat template 没套）
2. loss 降但效果差：过拟合小数据集 / 没有评测集盲调
3. 训完答非所问：template 与推理时的 prompt 格式不一致（**训练格式≠推理格式是第一大翻车现场**）
4. 显存爆：per_device_batch 太大没有梯度累积
