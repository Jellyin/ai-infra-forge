# Day 26 · 毕业项目（capstone）I——方案设计

> 目标：写一份「小型训练+推理平台」的完整技术方案。**这是你面试的旗舰证据**——比任何背题都值钱。

## 项目题目（固定选题，保证可比性）

> 为一家 200 人算法团队的公司设计并实现「AI 算力平台 MVP」：支撑 3 个业务线的推理服务（峰值 500 QPM）+ 算法团队日常微调（月 2000 卡时）。预算 500 万，12 张 A100-80G 已到位。

## 今天的产出：一份技术方案文档（含五部分）

### 1. 需求翻译（把业务语言变成技术约束）

| 业务说法 | 技术约束 |
|---------|---------|
| 「推理不能挂」 | SLO：可用性 99.9%、TTFT P99 < 3s |
| 「算法要训模型」 | 训练队列：gang 调度、月 2000 卡时、checkpoint 必备 |
| 「500 QPM 峰值」 | 容量：按 Day 8 SLO 法倒推卡数 |
| 「预算 500 万」 | 约束：优先优化后采购（Day 25 论证法） |

### 2. 架构图（四层，把 30 天学的都放进来）

```
入口层：API 网关（图像/文本闸门、限并发、SSE）
推理层：vLLM 池（量化选型、KEDA 按排队伸缩、多 adapter）
训练层：Volcano gang + 队列配额 + checkpoint 池 + 数据缓存
支撑层：监控（DCGM+服务双层）、FinOps 计量、演练预案
```

### 3. 容量推导（三本账，必须写出计算过程）

- **推理账**：500 QPM → 峰值 token 吞吐 → 卡数（用 Day 2 的拐点法数据）
- **训练账**：2000 卡时/月 → 排队模型（Day 19 的 P50/P90）
- **混部账**：昼夜互补可省多少（Day 25 的让渡计算）

### 4. 技术选型（每个选型带一句「为什么不是 B」）

例：调度选 Volcano——为什么不是原生 K8s？（gang 硬需求）；推理引擎选 vLLM——为什么不是 TRT-LLM？（生态与团队维护成本）；存储选「对象存储+本地缓存」——为什么不是全 Lustre？（成本与运维复杂度）

### 5. SLO 与验收（怎么算「做成了」）

可用性/性能 SLO + 平台北极星（排队 P50、MFU、GPU·时成本）+ 三个风险与预案（XID/网络互扰/坏 checkpoint——对应 Day 23 演练场景）
