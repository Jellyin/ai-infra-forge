# 里程碑 18 · 可观测与成本运营

> **本里程碑的交付物**：① 一次问答的全链路追踪图 ② 质量/延迟/成本三张运营看板（含阈值）③ 单次问答成本计算式与归因口径 ④ 容量规划表（峰值余量）⑤ 告警分级与响应动作表。
> **验收标准**：拿到一次「变慢/变贵」的投诉，能靠这三张看板在十分钟内指出慢在哪一跳、贵在哪一块，并说出该叫谁。

## 18.1 一次问答经过哪些跳：没有这张图就无法定位

上线后才真正开始，是因为**问题只有在真实流量下才暴露**。定位的前提是把一次问答切成有名字、有耗时的跳：

```
[网关] → [鉴权/租户解析] → [限流] → [缓存查询] → [检索]
   → [rerank?] → [prompt 组装] → [推理: queue_wait | prefill | decode] → [后处理] → [审计落库]
```

每一跳都必须能回答两个问题：**耗时是多少**、**失败怎么表现**。这不是画给自己看的，是**当一个投诉进来时，你能立刻指着某一跳说「是它」**。关键是把推理再拆成 `queue_wait / prefill / decode` 三段——否则「慢」永远只在排队和生成之间互相甩锅。

## 18.2 三张核心看板与阈值

质量、延迟、成本必须**同屏**，因为优化任意一个都会拉扯另外两个：

| 看板 | 关键面板 | 阈值（示例，按 SLO 定） |
|---|---|---|
| **质量** | 拒答率、引用覆盖率、用户反馈分、缓存误命中申诉数 | 拒答率突增 >20% 告警；引用覆盖率 <90% 告警 |
| **延迟** | TTFT P50/P95、端到端 P95、分环节耗时、queue_wait 占比 | TTFT P95 ≤ 2s；queue_wait 占比 >30% 说明要先调调度 |
| **成本** | 单次成本、日/月成本、按租户与场景成本、缓存命中率 | 单次成本日环比 >30% 告警；命中率骤降告警 |

**阈值不是摆设，是行动触发器**：看不到阈值触发后的动作，就等于没有阈值。

## 18.3 成本归因：先分清自建与按量，两种算法不同

自建 vLLM 的成本大头是 **GPU 时间**，不是 token，所以别照搬按量 API 的算法：

```
# 自建（按 GPU 卡时摊销）
单次生成成本 ≈ (GPU 卡时单价 ¥/卡·时 × 卡数 × 观测时长) / 该时段完成请求数
单次检索摊销 ≈ 向量库月成本 / 月检索次数 + 索引存储月成本 / 月文档数
单次总成本 ≈ 单次生成成本 + 单次检索摊销

# 若走按量 API（回退路径）
单次成本 = prompt_tokens × 输入单价 + completion_tokens × 输出单价
```

**归因到租户/场景是运营的前提**，口径要定死：

```
租户月成本 = Σ(该租户请求占用的 GPU 秒 × 卡时单价 / 3600)
           + Σ(该租户 token × 单价)          # 走按量时
           + 向量库分摊(按租户索引体积 或 请求占比，二选一，别混用)
```

模型分级是最大的成本杠杆：**简单问题用小模型、复杂问题才上大模型**，能直接改变上式里的「卡时单价 × 卡数」。

## 18.4 PromQL 查询清单

只列有把握的函数，**指标名按你实际埋点替换**：

```promql
# 端到端 P95
histogram_quantile(0.95, sum by (le) (rate(qa_e2e_duration_seconds_bucket[5m])))
# 分环节 P95（先看 queue_wait 占比，判断是排队还是生成慢）
histogram_quantile(0.95, sum by (le, stage) (rate(qa_stage_duration_seconds_bucket[5m])))
# 拒答率
sum(rate(qa_requests_total{outcome="refused"}[5m])) / sum(rate(qa_requests_total[5m]))
# 缓存命中率
sum(rate(qa_cache_hits_total[5m])) / sum(rate(qa_requests_total[5m]))
# 每租户 token 速率（成本归因的原料）
sum by (tenant_id) (rate(qa_tokens_total[5m]))
# 每租户在飞请求（判断谁在刷）
sum by (tenant_id) (qa_inflight_requests)
```

**GPU 利用率/显存** 这类指标通常来自 vLLM 自带 metrics 或 DCGM exporter，命名各家不同——**先确认你的 exporter 暴露了什么再写查询**，不要照抄别人的指标名。

## 18.5 容量规划：并发峰值与显存是硬约束

容量不是算 QPS，是算**并发槽位够不够塞进显存**：

```
峰值并发槽位 = 峰值 QPS × 单请求平均占用时长(s)
并发上限 ≈ (可用显存 − 权重占用) / (单请求平均上下文 × KV 每 token 占用)
  可用显存   ≈ 卡数 × 单卡显存 × gpu_memory_utilization
  权重占用   ≈ 参数量 × 精度字节数（FP16≈2B/参数）
  建议峰值余量 = 并发上限 / 峰值并发需求 ≥ 1.5
```

上式是**量级估算**，KV 每 token 占用要按你的模型实测（层数、hidden、精度、是否 GQA 都影响）。余量小于 1.5 就要提前扩，否则第一个促销日就是事故。

## 18.6 告警分级：什么必须半夜叫人

| 级别 | 例子 | 响应 |
|---|---|---|
| **P0 半夜叫人** | 全站错误率 >5% 持续 5min；TTFT P95 超 SLO 两倍持续 10min；拒答率突增 | 立即拉起，先止损再定位 |
| **P1 值班群** | 单租户配额打满、缓存命中率骤降、单次成本日环比 >30% | 工作时间内响应，当天处理 |
| **P2 工单** | 引用覆盖率缓慢下滑、单点慢查询趋势 | 排期优化 |

判据只有一条：**它会不会直接影响用户拿到答案**。会，就是 P0；只是「贵了」或「趋势不好」，降级。

## 18.7 本里程碑的判断力

- 「最近变慢了」→ 先看分环节 P95，**是排队涨还是 decode 涨**，别直接扩机器。
- 「账单涨了」→ 先拆 GPU 卡时与 token 两块，再看是哪个租户/场景，别先怀疑缓存。
- 看到只有延迟看板没有质量看板，说明还没上线——**质量信号缺位，优化就是盲飞**。
- 任何告警没有写「谁来做什么」，就还不是告警。
