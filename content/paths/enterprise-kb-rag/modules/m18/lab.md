# 🧪 动手实验 · 里程碑 18

> **本里程碑的交付物**：① 一次问答的全链路追踪图 ② 质量/延迟/成本三张运营看板（含阈值与触发动作）③ 单次问答成本计算式与租户归因口径 ④ 容量规划表（标明峰值余量）⑤ 告警分级与响应动作表。
> **验收标准**：拿一次真实投诉，你能在十分钟内指着链路图的某一跳说「是它」，并从成本看板指出钱花在哪个租户/场景；容量表能回答「余量还剩多少、什么时候要扩」。
>
> 三档任选：**档位 A 真实项目**（有真实流量与账单）／**档位 B 本地练习**（起 Prometheus/Grafana 或用脚本给每次问答打点分环节耗时）／**档位 C 纸上评审**（30 分钟，给一组追踪与成本数据让你定位）。

---

## 档位 A · 真实项目（推荐）

### 1. 给一次问答打上 trace，先能回答「慢在哪一跳」

按 guide 18.1 的链路，在网关给每次请求生成 `trace_id`，逐跳埋耗时。**最低可用版本**是打点下面几段：

```text
trace_id, tenant_id, stage, duration_ms, outcome
retrieval / rerank / prompt_build / queue_wait / prefill / decode / postprocess
```

跑一天后，挑出 P95 最慢的 5 条 trace，**逐条画成时间线**。验收点：你能说出「这条 8.2s 里，检索 0.3s、queue_wait 4.9s、decode 3.0s」——而不是「大概推理慢」。

### 2. 把三张看板建起来（质量/延迟/成本同屏）

用 guide 18.4 的 PromQL 起步，至少做出这几块，并**每块都写阈值与触发动作**：

| 看板 | 必备面板 | 你的阈值 | 触发后动作 |
|---|---|---|---|
| 质量 | 拒答率、引用覆盖率、反馈分 | | |
| 延迟 | TTFT P95、端到端 P95、分环节 P95、queue_wait 占比 | | |
| 成本 | 单次成本、按租户成本、缓存命中率 | | |

### 3. 算一次真实的单次成本，并做归因

按 guide 18.3 的公式，用真实数据填：

```text
单次生成成本 = 该时段 GPU 卡时费 / 该时段完成请求数
租户月成本   = Σ(该租户 GPU 秒 × 卡时单价 / 3600) + 向量库分摊
```

**归因口径要二选一并写死**（按索引体积 或 按请求占比），否则每次算出来都不一样。给出**一个可执行的优化方向**：降级小模型、提命中率、还是砍上下文。

### 4. 容量规划表

用 guide 18.5 的公式估算并发上限，填一张表：

| 项 | 值 | 来源 |
|---|---|---|
| 峰值 QPS | | 监控 |
| 峰值并发槽位 | | QPS × 单请求占用时长 |
| 并发上限（显存推导） | | 实测 KV 每 token |
| 峰值余量 | | 上限 / 需求，目标 ≥1.5 |

### 5. 定告警分级，并做一次「半夜该不该叫」的排练

按 guide 18.6 把现有告警归到 P0/P1/P2，**每条写清「谁在什么时间做什么」**。排练一次：人为制造 P0 条件，看是否真的会响、响了谁接。

## 档位 B · 本地练习

### 路线 B1：本地观测栈

```bash
# 起 Prometheus + Grafana，抓本地推理服务的指标端点
docker compose up -d prometheus grafana
# 用一条查询验证数据通了（指标名按你的 exporter 替换）
curl -sG http://localhost:9090/api/v1/query \
  --data-urlencode 'query=sum(rate(qa_requests_total[5m]))' | jq '.data.result'
```

没有自然流量，就用压测脚本（见 m17 lab）制造，观察三张看板随并发怎么动。

### 路线 B2：无观测栈，用脚本做「分环节耗时」分解

不起 Prometheus，写个脚本给单次问答的每一跳打时间戳，循环跑 200 次，输出每段的 P50/P95。**价值在于练「把一次慢拆成几段、找出最大的一段」**，而不是练 Grafana。

## 档位 C · 纸上评审（30 分钟）

一次投诉：「用户觉得慢，而且这个月账单翻倍。」下面是一组追踪与成本数据，指出慢在哪一跳、成本涨在哪一块：

```text
一次慢请求的追踪（总 9.1s）：
  检索 0.25s | rerank 0.10s | prompt 组装 0.05s
  queue_wait 5.6s | prefill 0.4s | decode 2.6s | 后处理 0.1s

成本环比（上月 → 本月）：
  GPU 卡时费    ¥8,000 → ¥14,000
  向量库费用    ¥1,200 → ¥1,300
  prompt_tokens 均值  1,800 → 2,100
  completion_tokens 均值 400 → 420
  缓存命中率    38% → 12%
  请求数        持平的 +2%

同期运维动作：为「更准」把 top_k 从 6 提到 12，并新上了一版更大模型的实验开关。
```

<details><summary>对照答案（先写完再看）</summary>

1. **慢在 queue_wait（5.6s，占 62%）**，不是 decode（2.6s）。这指向**排队**而非算力：`max_num_seqs` 太小、或大模型实验开关拉长了单请求占用、或并发上来了但槽位没扩。**先查槽位与调度参数，别急着加副本**（利用率大概率没打满）。
2. **成本涨在 GPU 卡时（+75%）**，而向量库几乎没动。结合「top_k 6→12」和「大模型开关」：① 更大模型直接抬高卡时单价/占用；② top_k 翻倍拉长 prompt，进而拉长 prefill 与 KV 占用。
3. **缓存命中率从 38% 掉到 12%** 是关键线索——命中率骤降意味着大量请求回源打 GPU，这与卡时上涨一致。要查是不是 top_k 或 prompt 版本变了导致缓存键/前缀失配（m17 的 `index_snapshot_id`/`prompt_version`）。
4. **completion_tokens 几乎没变**，所以「账单涨」不是生成变长，而是**输入变长 + 命中率下降 + 更大模型**三者叠加。优化方向：把大模型实验收敛为分级策略（简单问题走小模型），top_k 回落到实测最优，并修复缓存失配。
5. **运维动作缺少对应的看板与阈值**：top_k 与模型变更前若有三张看板与告警，命中率骤降当天就会被发现。

</details>

## 交付物验收清单

| 交付物 | 通过标准 | 你的产出 |
|---|---|---|
| 全链路追踪图 | 每跳有名字与耗时；能对最慢的 5 条 trace 指出瓶颈跳 | |
| 三张看板 | 质量/延迟/成本同屏，每块含阈值与触发动作 | |

> 收束：可观测不是把指标铺满，而是让「慢、贵、错」各自有一条**十分钟内能走到的证据链**。走到这里，这套知识库才真正从「能跑」变成「能运营、能交接」。
