# 🧪 动手实验 · 里程碑 17

> **本里程碑的交付物**：① 问答服务接口契约 ② 并发/批处理配置说明 ③ 语义缓存键设计与失效策略 ④ 租户级限流配置 ⑤ 失败降级矩阵。
> **验收标准**：接口契约能被第三方照着重写一份客户端；能拿出一张并发-延迟曲线说明「为什么现在不加副本」；能演示一次缓存失效与一次限流隔离；能说清模型挂掉时用户看到什么。
>
> 三档任选：**档位 A 真实项目**（有自建 vLLM 与真实租户）／**档位 B 本地练习**（起本地推理服务 + Prometheus/Grafana，或仅用脚本做耗时分解）／**档位 C 纸上评审**（30 分钟，纯判断力训练）。

---

## 档位 A · 真实项目（推荐）

### 1. 先把契约写出来，再用 curl 把它跑通

按 guide 的骨架补全你的接口契约，**至少定死 `citations[]`、`usage`、`trace_id` 三个字段**。然后手工验证流式：

```bash
curl -N -sS http://localhost:8000/v1/qa \
  -H 'Content-Type: application/json' -H 'X-Tenant-Id: acme' \
  -d '{"tenant_id":"acme","user_id":"u1","query":"M4 评审定的超时是多少","stream":true}'
```

**通过标准**：先收到 `event: citation`，再是一串 `event: token`，最后 `event: done` 带 `usage` 与 `trace_id`。若引用在答案之后才到，回 guide 17.1 重排。

### 2. 画并发-延迟曲线，公开为「要不要加副本」辩护

用固定模型、逐步加压，记录每一档的四个数：

| 并发 | 平均 TTFT | P95 队列等待 | P95 decode | GPU 利用率 |
|---|---|---|---|---|
| 1 | | | | |
| 8 | | | | |
| 32 | | | | |
| 64 | | | | |

**结论要落到 guide 17.2 的那张判断表**：如果「并发涨而 TTFT 涨、但 GPU 利用率仍低」，说明是排队上限的问题，**不该加副本**，该调 `max_num_seqs`。

```bash
# 简易压测：并发打同一端点，观察 P95 与利用率
hey -z 60s -c 32 -m POST -T application/json \
  -d '{"tenant_id":"bench","user_id":"u","query":"ping"}' \
  http://localhost:8000/v1/qa
```

### 3. 语义缓存：亲手制造一次误命中，再修好它

- 打开缓存，先记录命中率与「缓存月省」的估算值。
- **故意制造误命中**：构造两句话义近似但意图相反的 query（如「如何申请延期」/「如何撤销延期」），看阈值 0.85 是否把后者命中成前者。
- **修**：把阈值调到 0.90，并把 `acl_scope` 与 `index_snapshot_id` 加进键，重放同一组 query，确认误命中消失、命中率未崩。

### 4. 租户限流与隔离演练

给两个租户分别设 `rpm`/`concurrent`，用脚本让**租户 A 打到超限**，同时观察租户 B 的成功率。**验收点：A 被 429 时，B 的 P95 不恶化**。若 B 也变慢，说明限流只做了全局限流，没有按租户排队。

### 5. 降级演练（至少做两次）

拔掉向量库连接、或把生成超时压到 1s，确认服务按 guide 17.5 的矩阵行动，且**用户看到的是明确的降级提示**，不是假装成功的空答案。

## 档位 B · 本地练习

### 路线 B1：本地起推理 + Prometheus/Grafana（推荐）

```bash
# 1. 起一个本地 OpenAI 兼容的推理服务（显存不够就用小模型或 CPU）
docker run --rm --gpus all -p 8000:8000 \
  vllm/vllm-openai:latest --model Qwen/Qwen2.5-1.5B-Instruct \
  --max-num-seqs 32 --enable-prefix-caching
# 2. 起观测栈，指标端点抓上面的服务
docker compose up -d prometheus grafana
```

在你的网关里把「队列等待」与「decode 耗时」**分别**打点，然后重跑压测，把曲线画进 Grafana。

### 路线 B2：无 GPU，只做耗时分解

不起模型，写个脚本模拟「检索 + prefill + decode」三段耗时，人为让某一段随并发线性上升，练习**从曲线读出瓶颈在哪一段**。这条路线的价值是练「拆延迟」的手感，不是练运维。

## 档位 C · 纸上评审（30 分钟）

下面是某次高峰的三条线索，找出问题：

```text
线索1 · 并发-延迟（同一模型，逐步加压）
  并发 16：TTFT P95 = 0.9s，GPU 利用率 42%
  并发 32：TTFT P95 = 1.4s，GPU 利用率 55%
  并发 64：TTFT P95 = 3.8s，GPU 利用率 61%
  运维结论：「GPU 没用满，加两个副本就行。」

线索2 · 缓存事件
  14:02 文档《离职流程 v3》发布
  14:05 缓存命中率不降反升，维持 38%
  14:20 用户投诉：问到「离职交接清单」，答案引用了 v2 的旧章节

线索3 · 限流
  限流只配了 global.rpm = 3000
  某租户用脚本刷了 2800/分钟，其余租户全部超时
```

<details><summary>对照答案（先写完再看）</summary>

1. **线索1：加副本是错的。** GPU 利用率从 42% 涨到 61% 却仍偏低，TTFT 却近乎翻三倍——瓶颈是**队列等待**（`max_num_seqs` 太小或调度参数），不是算力。加副本只是把同一个瓶颈复制两份，成本翻倍、缓解有限。应先调 `max_num_seqs`、开 `enable_prefix_caching`，再看利用率是否打满。
2. **线索2：缓存没有随文档更新失效。** 命中率不降反升，说明**没有事件驱动的失效**（文档更新未反查引用它的缓存项），也没有把 `index_snapshot_id` 进键。修正：文档发布时按反向索引清掉引用该 doc 的缓存项；键里加入索引版本；补 TTL 兜底。
3. **线索2 同时暴露引用陈旧**：即使命中，也应校验引用的 `index_snapshot_id` 与当前索引一致，否则拒绝命中、回源。
4. **线索3：限流维度缺失。** 只有全局 rpm，没有租户维度，一个租户就能吃满配额拖垮全站。要补 `tenant`/`user` 维度与 `tpm`（防长上下文），并对超限**显式 429 + Retry-After**。

</details>

## 交付物验收清单

| 交付物 | 通过标准 | 你的产出 |
|---|---|---|
| 接口契约 | 含流式事件序列、`citations[]`、`usage`、`trace_id`；第三方能照此写客户端 | |
| 并发/批处理配置 | 附一张并发-延迟表，并据此说明「加副本或不加」的理由 | |
| 语义缓存键与失效策略 | 键含租户/权限/索引版本；有反向索引 + TTL + 版本升维三件套；演示过一次误命中修复 | |
| 租户限流配置 | 双租户演练通过：A 超限时 B 的 P95 不恶化 | |
| 失败降级矩阵 | 至少两次真实降级演练，用户可见行为与矩阵一致 | |

> 收束：服务化的标志不是「能并发」，而是**每一个租户都刷不垮别人、每一次缓存命中都可被追责、每一次失败都有兜底**。做到这三点，才有资格进入可观测与成本运营。
