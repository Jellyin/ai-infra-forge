# 🧪 动手实验 · 里程碑 15

> **本里程碑的交付物**：① 低打扰反馈采集方案（含事件 schema）② bad case 归档表与归因流程 ③ 影子流量/灰度 A/B 方案（含对比口径与显著性）④ 反馈回流评测集的纪律 ⑤ 迭代节奏与责任人表。
> **验收标准**：任取一条线上的负面事件，你能沿日志追到「哪个问题、命中了哪些块、哪个环节出错」；且能说清「多久评一次、谁拍板、回滚条件是什么」。
>
> 三档任选：**档位 A 真实项目**（有线上流量，接真实埋点）／**档位 B 本地练习**（用日志文件模拟反馈采集与回流）／**档位 C 纸上评审**（30 分钟，纯判断力训练）。

## 档位 A · 真实项目（把闭环接起来）

### 1. 先定事件 schema，再埋点

埋点前先冻结字段（抄 guide 15.2 的 JSON）。**最小可用集合**必须含 `query_id`、`action`、`retrieved_chunk_ids`、`model_version`、`prompt_version`——缺 `query_id` 就无法回连，缺版本号就无法归因到某次改动。

上线后先做一次「回连演练」：随便挑一个 `query_id`，把它从反馈事件 → 提问原文 → 命中块 → 走的是哪个 prompt 版本，完整串一遍。**串不通，说明埋点白做。**

### 2. 每周把反馈聚合成 bad case 并归因

```bash
# 捞一周的负面事件（显式点踩 + 隐式异常）
python -m feedback.triage \
  --events feedback/events-2026-10-*.jsonl \
  --signals thumb_down,requery,followup,zero_cite_click \
  --out badcases/2026-10-17.jsonl
```

归因时对每条问四个问题，强制落到环节（guide 15.3 的表）：

```text
① gold 文档在不在 top-k？      不在 → 检索漏召（切分/向量/改写）
② 在但排第几？                 太后 → 排序错（rerank/k）
③ 进了拼装吗？                 没进 → 上下文丢失（预算/去重）
④ 证据有但答案编了吗？         编了 → 生成幻觉（提示词/模型/校验）
```

### 3. 定优先级，派活

把 bad case 按「归因环节 × 出现频次 × 答错代价」排序。**高频 × 高代价**先修；只高频不高代价的（措辞不礼貌）可以排后。每条都要有责任人与责任版本，否则闭环断在这一步。

### 4. 影子流量验证高风险改动

换模型或换切分前，先在旁路跑：

```bash
python -m eval.shadow \
  --shadow-log logs/shadow-2026-10-18.jsonl \
  --live-log  logs/live-2026-10-18.jsonl \
  --judge configs/judge.yaml --out reports/shadow.json
```

对比口径要提前写死：同一批 query，新链路 vs 现网，用同一 judge 评 + 关键子集人工复核。注意影子拿不到真实点击——它只能回答「新链路会不会更差」，回答不了「用户是否更喜欢」。

### 5. 灰度 A/B 与显著性

```bash
# 按 user_id 哈希分桶（同一用户稳定同组），而不是按请求随机
python -m eval.ab \
  --a buckets/a.jsonl --b buckets/b.jsonl \
  --metric faithfulness --guardrails latency_p95,false_refusal_rate \
  --alpha 0.05
```

先算 MDE（要检测多大提升需要多少样本），再看 p 值与置信区间；护栏恶化就不算赢。

## 档位 B · 本地练习（用日志文件模拟反馈与回流）

没有真实流量时，用一份模拟日志把闭环走通：

```bash
# 1. 造一批反馈事件（含点踩、重问、零引用点击三类信号）
python scripts/gen_feedback.py --queries evalset/gold-v1.jsonl --n 200 --out feedback/mock.jsonl

# 2. 聚合并归因
python -m feedback.triage --events feedback/mock.jsonl --out badcases/mock-badcases.jsonl
jq -r '.attribution' badcases/mock-badcases.jsonl | sort | uniq -c | sort -rn

# 3. 影子对比（用同一份 query 跑两条链路的结果文件）
python -m eval.shadow --shadow-log logs/mock-shadow.jsonl --live-log logs/mock-live.jsonl --judge configs/judge.yaml
```

**核心练习：把 bad case 回流成新题，并守住纪律。**

```bash
# 加的必须是「人工重标过 gold」的题，且只加不删、bump 版本
python -m evalset.append \
  --evalset evalset/gold-v1.jsonl \
  --new badcases/new-questions.jsonl \
  --require-human-gold --bump minor --out evalset/gold-v1.1.jsonl
```

回流后做两件事：① 从新增题里划出一部分进 held-out，永不参与调优；② 检查四类分布有没有被反馈带偏（别只加「投诉最多的那类」）。

> 这一档的价值：练「归因到环节」和「回流守纪律」这两件最容易被跳过的事。

## 档位 C · 纸上评审（30 分钟）

下面是三条真实的线下/线上信号，做归因并排出优先级：

```text
A. 很多用户搜「年假多少天」后，换问法再问「年休假有几天」——重问率高。
B. 一条点踩留言：「它引的是旧版流程，新流程早就改了。」
C. 有用户问「明年组织架构怎么调」，系统给了个具体答案，用户投诉「这个它不该乱答」。
D. 后台看到「引用点击率」本周从 22% 掉到 9%。
```

<details><summary>对照建议（先写完再看）</summary>

- **A** 大概率是**检索漏召或改写不足**：同义问法没匹配到同一批文档。归因环节是查询改写/向量召回；优先修，因为频次高。
- **B** 是**排序或时效性权重问题**：旧版文档被召回且排在前面。归因环节是排序/时效加权，或元数据缺少版本字段。要注意——这是**检索侧**问题，不是模型幻觉。
- **C** 是**该拒未拒（漏拒）**：不可答题给了答案。归因环节是拒答判据阈值；代价高（用户信任），优先级高。
- **D** 是最容易被误判的一条：引用点击率**下降**有两种相反解释——① 引用变少了/变差了（坏），② 答案更直接可信、用户不用点开核对了（好）。**不能只看一个隐式指标下结论**，要同时看引用覆盖率与正确率、以及同期点踩率。这正是「隐式信号要交叉验证」的典型。

排序建议：C（高代价）与 A（高频）并列优先，B 次之（需先确认版本元数据是否齐全），D 先做**指标交叉验证再决定**，别急着当事故处理。

</details>

### 最后：把闭环压成一句话

无论哪一档，结束前必须能填出这句——填不出说明闭环还没闭上：

> 「线上负面信号从 **__（埋点）** 来，每周由 **__** 归因到**链路环节**，高频×高代价的先修；高危改动先过 **__（影子流量）** 再过 **__（灰度 A/B，含护栏 __）**；验证过的优秀/失败案例**人工重标 gold 后只加不删**地回流评测集，并保留 **__% held-out**；由 **__** 拍板，回滚条件是 **__**。」
