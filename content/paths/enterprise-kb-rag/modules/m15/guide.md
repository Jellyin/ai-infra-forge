# 里程碑 15 · 在线反馈与持续改进闭环

> **本里程碑的交付物**：① 一套低打扰的反馈采集方案（含事件数据结构）② bad case 归档与归因流程 ③ 影子流量与灰度 A/B 方案（含对比口径与显著性）④ 反馈回流评测集的纪律 ⑤ 迭代节奏与责任人定义。
> **验收标准**：任意一条线上差评都能沿日志追溯到「哪个问题、命中了哪些块、哪个环节出问题」；且你能说清「多久评一次、谁拍板、回滚条件是什么」。

## 15.1 离线评测集的天花板

m13 的黄金集再精心，也是**你见过的问题**——线上的长尾、新口径、新问法都落在它之外。离线集管「已知不能退步」，线上反馈管「未知要靠发现」，两者不能互相替代：只靠离线会盲，只靠线上会被情绪带节奏。

## 15.2 低打扰的反馈采集

企业内网没人爱打分，第一条原则是**零打扰优先、一次点击封顶**：

- **显式**：👍/👎 一次点击完成；「纠错」藏在点踩之后才展开，别一上来就问「哪里不对」。
- **隐式**（免打扰，往往更诚实）：**引用点击率**（点引用核对说明在意证据）、**复制率**、**追问率**、**同问题重问率**（换个说法再问 = 上次没答好）。
- **不强制**：不弹窗、不做 NPS 问卷、不上星级评分。

关键不在收得到，而在**收了能定位**。每条反馈必须带足上下文，否则就是一堆无法归因的情绪：

```json
{"event_id":"evt-9f3a","ts":"2026-10-17T10:21:03Z","session_id":"s-77c","query_id":"q-51b",
 "user_id_hash":"a1f9…","action":"thumb_down","target":"answer","citation_id":null,
 "latency_ms":1830,"channel":"web","model_version":"v3","prompt_version":"p7",
 "evalset_version":"2026.09","retrieved_chunk_ids":["hr-policy-v3#s4-c2","hr-policy-v2#s1-c1"],
 "gold_rank_in_topk":3,"extra":{}}
```

`query_id` 是主键，向前能查到问题原文、命中的块、走的哪条链路、当时的检索排名。**没有这些字段，点踩就只是点踩，不是可改进的数据。** 隐私上 `user_id` 做哈希、内容脱敏、设保留期。

## 15.3 bad case 归档与归因：必须落到环节

每周把 👎 与隐式异常信号（重问、追问、零引用点击）聚合成 bad case，逐条归因。**「归因到模型」等于没归因**——要落到具体环节：

| 归因类别 | 判定线索 | 归属环节 |
|---|---|---|
| 检索漏召 | gold 文档不在 top-k | 切分 / 向量 / 查询改写 |
| 排序错 | gold 在 top-k 但排太后 | rerank / k 值 |
| 上下文丢失 | gold 在 top-k 却没进拼装 | 长度预算 / 去重（m10） |
| 生成幻觉 | 证据里有，答案却编了 | 提示词 / 模型 / 生成后校验（m11） |
| 引用错 | 引用了不支持结论的块 | 引用校验层（m11） |
| 该拒未拒 / 误拒 | 不可答却答 / 可答却拒 | 拒答判据阈值（m10） |
| 权限误伤 | 有权看却被过滤 | 权限过滤表达式（m12/m16） |

归档表每行含 query、类型、归因类别、证据（命中的块与排名）、修复动作、责任版本。归因到环节才能派活；派不了活，闭环就断了。

## 15.4 影子流量：旁路跑，不影响用户

新链路对**同一批线上问题**在旁路重跑一遍，结果**不返回给用户**，只做对比。适合高风险改动（换模型、换切分、换 rerank）上线前验证。

- **对比口径**：同一 query 的「新链路结果」与「现网结果」用同一 judge 与人工评；或用「预测会被点踩的比例」当代理指标。
- **好处**：零用户风险，能拿到真实问题分布。
- **坏处**：拿不到真实用户反馈（用户没看到新结果），且**成本翻倍**。
- **纪律**：影子结果不得写进面向用户的日志或缓存；只对**有权限**的流量做，输出同样脱敏。

## 15.5 灰度与 A/B：分流量口径与显著性

- **分流量口径**：按 `user_id` 哈希分桶，让**同一用户稳定落在同一组**——否则同一人来回切会污染体验与反馈，也让「组间差异」混入「切换混乱」。别按请求随机分。
- **样本量与显著性**：先算「要检测多大提升需要多少样本」（MDE），别看到 3% 就宣布赢；报**置信区间与 p 值**，样本不够就别声称显著。
- **护栏指标同期看**：延迟、错误率、拒答率、漏拒率一起看；实验组快了但拒答变多，不算赢。
- **单变量**：一次只改一个东西，否则无法归因。

## 15.6 反馈回流评测集：加题要守纪律

线上反馈是评测集的**新增题源**，回流要防两件事——**带偏**与**过拟合**：

1. **只加不删**（除题本身有错）；新增题要与**线上分布对齐**，不能只收「抱怨最多的那类」，否则评测集会偏向投诉集中区而失去代表性。
2. **四类都要收**，包括不可答题——反馈里最有价值的往往是「该拒答却没拒」的投诉。
3. **gold 必须人工重标**：绝不拿模型当时的输出当 gold（会把错误固化进评测集）。
4. **防止评测集过拟合**：每轮都把失败题加进去反复调，系统会在这批题上过拟合。对策二选一——留 **held-out 集**（永不参与调优），或采用**滚动窗口**（新题做验证、旧题退役）。

## 15.7 迭代节奏与责任人

节奏由**改动风险与成本**决定，不由日历决定：

| 改动类型 | 验证方式 | 建议节奏 |
|---|---|---|
| 提示词 / 阈值微调 | 跑 CI 门禁 | 每次改动 |
| rerank / k / 拼装策略 | 门禁 + 小流量灰度 | 周级 |
| 换模型 / 换切分 / 换向量库 | 影子流量 + A/B | 双周～月度 |

**谁拍板**要写清（RACI）：质量指标是否达标的**判定权**归质量负责人；是否上线、何时回滚归技术负责人/业务 owner；涉权限或合规的改动要合规会签。每次迭代留一条**决策记录**——改了什么、指标怎么变、谁批的、**回滚条件是什么**。没有回滚条件的上线，不叫上线，叫赌博。

## 15.8 本里程碑的判断力

- 反馈面板只有点赞数、没有 `query_id` 与命中块，直接判定：**这套反馈不可归因，等于没收**。
- 看到 bad case 结论写「模型能力不足」，追问：**是漏召、排序错、拼装丢块，还是幻觉？**
- 有人要「先全量上线再说」，反问：**影子流量跑了吗？护栏指标谁看？**
- 评测集每周加题却从没有 held-out，提醒：**你正在过拟合评测集**。

真正的闭环是「线上发现 → 归因到环节 → 改进 → 灰度验证 → 回流评测集」这个越转越快的轮子。
