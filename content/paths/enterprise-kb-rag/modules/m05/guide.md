# 里程碑 5 · 切分策略：粒度、重叠与父子块

> **本里程碑的交付物**：① 三类文档的切分策略选择与理由 ② 可复用的切分配置 ③ 父子块存储结构与检索流程 ④ 不可切分内容清单 ⑤ 切分参数对比实验设计与结论。
> **验收标准**：同事看你的切分配置，能说出「为什么是这个块大小、这个 overlap」；且你能亮出「不同参数 → 召回指标」的对照数字。

## 5.1 切分是召回与可读性的共同约束

切分同时服务两个相反目标：**召回**要块小、语义集中；**生成**要块完整、有上下文。
判据：**切分是给「检索」切的，不是给「入库」切的**——块大小是**在真实提问分布上召回最好**的那个。

## 5.2 四种策略：适用与代价

| 策略 | 适用 | 代价 / 风险 |
|---|---|---|
| 固定长度 | 结构极乱、纯流水文本 | 无视语义，句子被腰斩 |
| 递归切分 | 结构一般的正文（默认主力） | 参数要调，仍有边界损伤 |
| 结构感知（按标题） | 有清晰层级的文档（解析阶段已恢复） | 依赖 m04 的 `section_path`；某节过长需二次切 |
| 语义切分 | 无标题的长论述 | 需额外模型/计算，成本高，收益不稳定 |

**推荐主线**：能结构感知就结构感知（先按标题切节），**节内再套递归切分**控上限——先结构、后长度。

## 5.3 可抄的切分配置

结构感知打底、递归兜底：

```python
from langchain_text_splitters import (
    MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter,
)

# ① 先按标题切节（层级进 metadata）
header_split = MarkdownHeaderTextSplitter(
    headers_to_split_on=[("#", "h1"), ("##", "h2"), ("###", "h3")],
    strip_headers=False,
)
sections = header_split.split_text(md_text)

# ② 节内再递归（只对过长节）
recursive = RecursiveCharacterTextSplitter(
    chunk_size=800,
    chunk_overlap=120,     # ≈ 15%
    length_function=len,   # 按 token 计则换 tokenizer 计数
    separators=["\n\n", "\n", "。", "！", "？", "；", " ", ""],  # 中文标点要补
)
chunks = []
for sec in sections:
    chunks.extend(recursive.split_documents([sec]))
```

**注意**：`chunk_size` 单位由 `length_function` 决定——`len` 是**字符数**，tokenizer 是 **token 数**，别混用。默认分隔符缺中文标点，**不补 `。！？；` 会把整段中文当一个单位**。

## 5.4 overlap 的作用与副作用

**作用**：防止一个事实落在两块边界上、被各切一半，谁都没召回完整信息。

**副作用**（常被忽略）：

| 副作用 | 后果 |
|---|---|
| token 重复计入 | 索引膨胀、embedding 成本上升 |
| 近重复块 | 检索 top-k 被近似块占满，挤掉真正不同的证据 |
| 上下文浪费 | 拼装时同样的句子出现两次，浪费生成预算 |
| 评测失真 | 黄金集里相邻块互为近重复，recall 虚高 |

**经验区间：overlap ≈ chunk_size 的 10%–20%**；超过 ~25% 通常得不偿失，先用 5.8 的实验验证召回增益是否值回代价。

## 5.5 父子块（small-to-big）：小块检索、大块生成

痛点即 5.1 的矛盾：小块好检索但信息不全，大块向量被稀释。父子块把两者拆开：

- **子块**（小，~200–300 token）：入向量库，用于**检索**；
- **父块**（大，~1000–2000 token）：**只存不检索**，命中子块后取回其父块**交给生成**。

```python
# 子块（可检索），parent_id 指回父块
child = {
    "id": "d100#sec2#c03",
    "text": child_text,                 # 检索用
    "embedding": vec,
    "payload": {
        "parent_id": "d100#sec2",
        "doc_id": "d100",
        "section_path": ["3 计费", "3.2 跨区费率"],
        "page": 12,
    },
}
# 父块（不检索）：进 KV / 关系表
parent = {
    "id": "d100#sec2",
    "text": parent_text,                # 交给生成
    "section_path": ["3 计费", "3.2 跨区费率"],
}
```

**检索流程**：召回子块 top_k（如 20）→ 去重收集 `parent_id` → 取回父块 → 按父块粒度重排 → 拼上下文。

**收益**：小块保检索精度、大块保生成完整性。**成本**：多一次「子→父」查询跳、文本存两份，**父块数量须按 token 预算封顶**，否则拼装超窗。

## 5.6 表格与代码：绝不可按长度硬切

1. 表格与代码块**整块保留**，作为独立 chunk（`type=table/code`）；
2. 真的过大时**按行/按函数拆**，但**每个子块重复表头行 / 补全上下文**；
3. 用 `atomic=true` 标记，让切分器**跳过长度切分**。

**判据**：切完读不出「这行属于哪个表头/这段属于哪个函数」，这次切分就是错的。

## 5.7 块大小与 embedding 模型上下文的关系

embedding 模型有**最大输入 token 数**；**块超限会被静默截断**——尾部不入向量，等于对检索不可见。所以 `chunk_size` 要在**嵌入模型 tokenizer** 度量下、留余量地小于上限。中文上，多数中文 tokenizer「1 字 ≈ 1 token」，按**字符**设的 800 可能已超过 512 上限而不报错。

**做法**：用该 tokenizer 量块长分布（见 commands），确认 P99 在上限内；最稳妥是让 `length_function` 按该 tokenizer 计数。

## 5.8 切分参数的评测：控制变量，别凭感觉

**先建黄金集**：一批 `(query, 相关块/段落)` 对。指标：

- **recall@k**：相关块是否落在 top-k 内（切分最直接的受害者就是召回）；
- **MRR / context_precision**：相关块排得靠不靠前；
- **近重复率**：top-k 里近似块占比（overlap 过大的报警器）。

**控制变量实验**：固定 embedding、检索器、k 与语料，**一次只改一个参数**：

| 变量 | 取值（示例） | 固定 |
|---|---|---|
| chunk_size | 256 / 512 / 800 / 1200 | overlap=15%、递归、k=5 |
| overlap | 0 / 10% / 20% / 40% | chunk_size=800，其余同 |
| 策略 | 固定长度 / 结构感知 | 参数同上 |

每格记录：块数、recall@5、近重复率、平均块长、索引体积。**选型规则**：满足 recall 目标下取**块数最少**的那组，并盯住近重复率别爆。

## 5.9 本里程碑的判断力

- 看到 `chunk_size=800` 不说单位，先问：**字符还是 token？嵌入模型上限多少？**
- 有人把 overlap 调到 30% 以上，追问：**近重复率和索引体积涨了多少？召回涨了几个点？**
- 检索准但答案读不完整，考虑**父子块**；答案完整但检索不准，先把块切小。
- 看到表格/代码被按长度切开，直接判错——**不可切分内容整块保留**。
