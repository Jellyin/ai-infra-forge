# 里程碑 7 · 基线检索与召回测量

> **本里程碑的交付物**：① 黄金集（query → 正确块 id 的标注）② 召回@k 与 MRR 基线报告 ③ 失败归因表（「语料缺失」vs「检索失败」）④ 一条可重复运行的评测脚本 ⑤ 统一的检索日志格式。
> **验收标准**：任一同事用你的脚本与黄金集，能一键复现出同一组 recall@k / MRR 数字，并说得出「哪些 query 失败了、各自该归到哪一类原因」。

## 7.1 先有基线，才谈得上优化

没有基线数字，任何改动都是「感觉更好了」。基线的意义是把「改得是否有效」变成**可判定**的问题：改前 recall@5 = 0.62、改后 0.71 才算数。本里程碑不追求高指标，只追求**第一个可信数字 + 一套能重复跑的方法**。

## 7.2 recall@k 的分母到底是什么

```text
recall@k = |相关块 ∩ 前 k 个结果| / |该 query 的全部相关块|
```

- **分母是「应召回的文档数」**（黄金集标注的全部相关块），既不是 k，也不是库里总块数。
- recall@k **恒 ≤ 1**；相关块数 > k 时天然存在上限 < 1——所以 k 要结合「每个问题平均几个正确块」来定。
- 每个问题只有 1 个正确块时，recall@k 退化为**命中率 hit@k**（0 或 1）。很多口径说的「recall@5」其实是 hit@5，**报告里必须写清是哪种**，否则数字不可比。
- recall@k 顺序无关（只看进没进前 k）；关心排名第几要用 MRR。

## 7.3 MRR 的定义与适用场景

```text
RR(query) = 1 / rank ,  rank 是第一个相关结果的名次（从 1 开始）
            无相关结果则 RR = 0
MRR       = 所有 query 的 RR 平均值
```

- MRR 关心「**第一个**正确结果排多高」，对 top-1 极敏感：从第 5 名提到第 1 名，RR 从 0.2 升到 1.0。
- 适用：**每个问题基本只有一个正确答案**的查证类场景；不适用一题多块、且希望都进 top-k 的情况。
- 判据：**关心「召回全不全」用 recall@k，关心「第一个对不对」用 MRR。** 分级相关的 nDCG 需要等级标注，留给评测里程碑。

## 7.4 top-k 与相似度阈值：两个参数各管什么

| 参数 | 作用 | 调大的代价 | 调小的代价 |
|---|---|---|---|
| top-k | 返回多少条候选 | 延迟↑、上下文变长、噪声↑ | 漏召回的块↑ |
| 阈值 | 分数下限，低于则不返回 | 正确结果被挡掉、拒答率↑ | 低分噪声混进上下文 |

- 两种顺序：**先卡阈值再取 top-k**（宁缺勿错，适合高代价场景），或**先取 top-k 再卡阈值**（重覆盖度）；由 m01 定的答错代价决定。
- **阈值不能照抄**：量纲取决于度量——cosine ∈ [-1, 1]、dot 无界、L2 ≥ 0 且越小越近；换模型/度量/归一化都要重校准。
- 阈值过低是**隐蔽错误**：检索总会返回 k 条「最像的」，即使全不相关，看起来「有结果」，用户却拿到噪声。

## 7.5 「看起来像」不等于「答得对」

高相似度只说明向量方向接近，不说明内容回答了问题。典型反例：命中同名但**不同版本**的文档；命中相同关键词却讲另一场景；命中「我们不做 X」而问题问「X 怎么做」。所以**评测必须用人工标注的「正确块」，而不是模型觉得像**；「检索对了、生成答错」属于生成侧，留给答案评测里程碑。

## 7.6 召回失败的两类原因：语料没有 vs 检索不到

| 归因 | 现象 | 验证方法 | 修法 |
|---|---|---|---|
| **语料缺失** | 全库/原文检索都找不到 | 拿正确答案关键词去原始语料 grep | 补数据、补解析（常见于 PDF 无文本层） |
| **检索失败** | 内容在库里却没进 top-k | 用原句去库里查，能查到但排名靠后 | 改切分（m05）/换模型（m06）/加混合检索（m08） |

第三种隐患：答案**跨块被切断**，表现像检索失败，根因却在切分。**每条失败 query 都要落到这三类之一**；归因不清的先 grep 一遍——**不要一看到召回低就换模型**。

## 7.7 把基线固化成一条命令

日志格式（每次检索都留痕，是后续归因的原料）：

```jsonl
{"ts":"2026-10-18T10:00:00Z","query":"年假怎么请","k":5,"hits":[{"id":"c1024","score":0.83},{"id":"c88","score":0.79}],"latency_ms":41}
```

```python
import statistics

def recall_at_k(gold: set, got: list, k: int) -> float:
    if not gold:
        return float("nan")
    return len(gold & set(got[:k])) / len(gold)   # 分母 = 该 query 应召回的相关块数

def reciprocal_rank(gold: set, got: list) -> float:
    for i, cid in enumerate(got, start=1):
        if cid in gold:
            return 1.0 / i
    return 0.0

def evaluate(golden, retrieve, k=5):
    R, MRRs, report = [], [], []
    for item in golden:                           # item = {query, gold_ids:[...]}
        got = retrieve(item["query"], k=k)        # 返回块 id 列表，按相关度降序
        r  = recall_at_k(set(item["gold_ids"]), got, k)
        rr = reciprocal_rank(set(item["gold_ids"]), got)
        R.append(r); MRRs.append(rr)
        report.append({"query": item["query"], "recall": r, "rr": rr, "hits": got})
    return {"recall@k": statistics.mean(R), "mrr": statistics.mean(MRRs), "detail": report}
```

**固化要求**：命令进版本库；黄金集改动要在报告里标出，否则新旧数字不可比。每次改切分/换模型/加策略，都先跑这条命令再决定是否合入。

## 7.8 本里程碑的判断力

- 有人报「改成混合检索效果更好了」，先追问：**基线 recall@k 是多少、现在多少？** 没有两个数字就没有结论。
- top-k 取多少？**先定延迟与上下文预算，再量噪声代价**，不是拍脑袋取 10。
- 召回低先别换模型：**先在原始语料里 grep 一条**，看是没数据还是没检索到。
