# 里程碑 16 · 多租户与权限落地

> **交付物**：① 三层隔离选型（含升级触发条件）② 二维权限模型 ③ 过滤表达式与不可绕过验证 ④ 权限变更传播方案与生效 SLO ⑤ 删除请求端到端传播 ⑥ 审计日志表结构与隐私边界。
> **验收标准**：能画出三层隔离并说明选型；按权限检索并通过越权测试；说明权限变更**多久**生效、怎么验证；跑通删除的端到端传播；审计既合规又不侵犯隐私。

## 16.1 隔离的三个层次

| 层次 | 做法 | 强度 | 成本 | 爆炸半径 | 噪声邻居 |
|---|---|---|---|---|---|
| **物理索引** | 每租户独立 collection/实例 | 最强 | 最高 | 单租户 | 无 |
| **逻辑集合** | 共享实例，按 collection/分区切租户 | 中 | 中 | 同实例全部租户 | 有 |
| **元数据过滤** | 共享 collection，块带 `tenant_id` 查询期过滤 | 最弱（正确性全压过滤） | 最低 | 全租户 | 有 |

**选型（写进 ADR）**：默认「逻辑集合 + 元数据过滤」，大租户单独 collection；合规极高的大客户升级独立实例。**必须写明「何时必须升级物理隔离」的触发条件**（合同/监管），否则会被合规客户逼到临时改架构。引擎差异：Milvus 有分区可做逻辑集合；Qdrant 无分区、多租户用 payload 上 `tenant_id` 索引 + 过滤（以你引擎能力为准）。

## 16.2 租户与用户的二维权限模型

第一维**租户**（组织/工作区）是一切检索的最小边界，跨租户无例外；第二维**主体**（用户/组/角色）决定租户内可见范围。每块挂：

```text
chunk.payload = { tenant_id, acl:[组id...], doc_id, sensitivity? }
# acl 含"租户内公共组"；空数组 = 不可见（缺省拒绝）
```

**有效可见集 = 用户所属组（含继承展开）∩ 该租户**。两铁律：① 缺省拒绝——`acl` 为空或不匹配即不可见（白名单，不是黑名单）；② 组继承在服务端展开，防环、有层级上限。

## 16.3 过滤表达式与不可绕过验证

```text
visible = chunk.tenant_id == user.tenant
      and any(g ∈ chunk.acl where g ∈ user.groups_expanded)
      and chunk.sensitivity <= user.clearance

# Milvus 风格： tenant_id == "acme" and ARRAY_CONTAINS(acl, "g-eng")
# Qdrant 风格： {"must":[{"key":"tenant_id","match":{"value":"acme"}},
#                       {"key":"acl","match":{"any":["g-eng","g-all"]}}]}
```

过滤与检索**同一次下发**（pre-filter，理由见 m12 12.2），`flt` 由服务端从会话身份构造。**不可绕过验证清单**（每条都要有自动化测试）：

| 检查项 | 做法 | 期望 |
|---|---|---|
| 身份不可伪造 | 请求体塞 tenant/groups | 被忽略，只认会话身份 |
| 过滤非后置 | 确认与检索同次下发 | 非 post-filter |
| 白名单语义 | 用户组为空时检索 | 0 命中（非返回全部） |
| 跨租户 | B 身份检索 A 的已知块 | 0 命中 |
| 语义绕过 | 把无权块向量当检索向量 | 仍 0 命中 |
| 组合逻辑 | `must` 改 `should` 再测 | 测试能捕获误放行 |

## 16.4 权限变更的传播延迟与强制刷新

真相源（IAM）是唯一定义；向量库里的 `acl` 是**反规范化副本**，必然陈旧。两种取舍：查询期实时读身份（撤权即时，但依赖 IAM、有延迟）／索引期固化 acl（快，但要等重标注才生效）。**推荐**：用户组在查询期展开（撤权即时），块 acl 存索引（容忍秒级传播），并加**强制刷新**——撤权/换组/离职即失效该主体缓存、把受影响 `doc_id` 打进 denylist。把「撤权到生效」写成 SLO（如 ≤60s），用脚本验证：**撤权 → 轮询检索 → 断言 SLO 内变 0 命中**。

## 16.5 删除请求（被遗忘权）的端到端传播

不是一条 delete，而是逐环验证的流程：

| 环节 | 动作 | 验证 |
|---|---|---|
| 1 真相源 | 删除 / 标记 tombstone | 源查询返回空 |
| 2 向量库 | 按 `doc_id` 过滤批量删 | scroll 该 doc_id → 0 |
| 3 缓存 | 失效查询/答案/嵌入/rerank 缓存 | 原查询重跑不再出现 |
| 4 派生数据 | 摘要、实体、图谱、评测样本 | 逐类清点 |
| 5 备份/日志 | 按保留策略处理，法务冻结的如实标注 | 记录策略与例外 |

收尾必须**反查**该文档特征并断言 0 命中。**如实写明备份与审计日志可能无法即时删除**——被遗忘权常受保留义务约束，诚实标注比假装删干净更重要。

## 16.6 审计日志：谁、何时、问了什么、命中了哪些文档

```sql
create table rag_audit (
  ts timestamptz not null default now(),
  request_id uuid primary key,
  tenant_id text not null,
  actor_id  text not null,        -- 稳定假名，不是邮箱/姓名
  query_hash bytea not null,      -- 查询文本哈希；原文加密短期保留
  retrieved_ids text[] not null,  -- 命中并进入上下文的 文档/块 id
  returned_ids  text[] not null,  -- 最终出现在回答里的引用 id
  decision  text not null,        -- allowed | blocked_by_acl | blocked_by_output_filter
  policy_ver text not null        -- 本次使用的权限/过滤规则版本
);
```

`retrieved_ids` 与 `returned_ids` **分开记**：前者证「有没有取到不该取的」，后者证「有没有说出去」（对应 m12 的两条路径）；`policy_ver` 便于复盘当时用的哪版规则。

## 16.7 审计的合规价值与隐私边界

合规价值：越权溯源、删除举证、访问报表、规则回归。**隐私边界**（写进设计文档）：① 最小化，查询原文加密 + 短期保留；② 目的限定，只用于安全与合规、**不得**用于绩效/监控；③ 禁止个体画像，不做「按人提问次数排行」、聚合设最小样本量；④ 读日志要被再审计，只有安全/合规角色可读；⑤ 对员工透明。

**判断力**：日志一旦变成「谁问得多」的排行榜就成了监控工具；**能证明「系统按规则运行」而不评判「人怎么用」，才算合格。**

## 16.8 本里程碑的判断力

- 问「多租户怎么做」，先反问：**物理还是逻辑？爆炸半径多大？何时必须升级？**
- 见「权限改完刷新一下」，追问：**多久生效、怎么验证、撤权到生效有没有 SLO？**
- 见「删了就删干净了」，追问：**缓存/嵌入/派生/备份/日志都处理了吗？怎么验证？**
