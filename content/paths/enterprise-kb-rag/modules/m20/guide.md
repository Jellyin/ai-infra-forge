# 里程碑 20 · 运营、演练与演进路线

> **本里程碑的交付物**：容量压测报告（含拐点）、故障演练方案与记录、内容运营机制、分阶段成本优化路线、演进方向选择依据、交接清单。
> **验收标准**：把一个陌生同事放进 oncall——他照着 runbook 能独立完成一次止血，并能说出「这个系统最脆弱的一环是什么、下一步补什么」。

## 20.1 容量压测：找拐点，而不是看平均值

「QPS 是多少」没意义；有意义的是「**在哪个并发量上 p95 开始非线性上升**」——即拐点。方法四条：

| 要点 | 做法 | 为什么 |
|---|---|---|
| **阶梯加压** | 每档稳定 2–3 分钟，记录 p50/p95/p99 与吞吐 | 平均值掩盖拐点 |
| **预热** | 先跑 5–10 分钟低负载 | 未预热结果失真 |
| **样本量够** | 每档至少数千请求 | 小样本的百分位与错误率不可信 |
| **固定变量** | 索引/模型/评测集版本全固定 | 否则两次压测不可比 |

**RAG 瓶颈多在检索与推理，不在 API 层。** 压测要**分层**：检索、生成、端到端。结论：**「并发 N 时 p95 突破 SLO，瓶颈在第几跳。」**

## 20.2 故障演练：把「会发生的坏」提前演一遍

演练的价值是**验证指标能否发现、预案能否止血、耗时多久**。四类必演场景：

| 场景 | 注入方式 | 要验证的 |
|---|---|---|
| 索引损坏/不可用 | 下线副本、损坏分片 | 降级是否触发、别名能否切回旧快照 |
| 模型不可用 | 停推理服务或注错 | 是否有降级、超时是否熔断 |
| 权限误配 | 故意放宽过滤条件 | 越权用例是否被拦（m16 双保险生效） |
| 源站变更 | 上游文档改结构/下线 | 增量接入是否报错、失败是否可见 |

**演练方案模板**：

```text
场景：<如「向量库主分片不可用」>
目标：验证 <指标能被发现> / <预案能在 X 分钟内止血>
影响面假设：<哪些提问者、哪些租户受影响>
注入步骤：1) … 2) …（可回退）
观测信号：<看哪个 SLI/质量指标，什么阈值算「坏了」>
止血动作：<命令/操作，谁执行>
计时：注入→发现→决定→止血完成（MTTR）
回退：如何恢复注入
改进项：<至少一条，带 owner 与截止日>
```

**判据**：一次演练没产生**至少一条改进项**，等于没演。

## 20.3 内容运营：知识库会「腐烂」

代码不会过期，知识会，覆盖度会**静默下降**。三个机制：

- **过期清理**：文档打 `last_verified` 与 `owner`，超 TTL 进复核队列，回答可提示「已 N 个月未复核」。
- **覆盖度补全**：从 m15 在线反馈取「无结果/低分」问题聚类，作下一轮接入清单——**真实缺口驱动**。
- **负责人机制**：每个语料源有 owner 负责新鲜度；无 owner 的源终会变噪声。

> 运营的度量不是「接了多少文档」，而是「**高频问题命中率**与**过期文档占比**」。

## 20.4 成本优化路线：按顺序做

| 阶段 | 手段 | 预期收益 | 风险 |
|---|---|---|---|
| 一 | **缓存**（结果/向量/前缀） | 高频直接命中，成本延迟同降 | 失效策略须正确 |
| 二 | **模型分级** | 简单问题走小模型 | 路由判错伤质量 |
| 三 | **批处理与预算闸** | 非实时任务批量化；单租户预算上限 | 过度限流会伤体验 |

**顺序原则**：先做**无损**的（缓存），再做**需评测护航**的（模型分级），最后做**影响体验**的（限流闸）。

## 20.5 演进方向：三种选择的适用条件

- **多模态**：仅当**高价值问题确实依赖图片/表格/扫描件**、文本路径已扎实时才做；否则给低频需求付全量成本。
- **Agent 化**：仅当问题需**多步操作**（查多系统、计算、调 API）时才值得；单跳问答引入 Agent 只是延迟成本。
- **微调/蒸馏**：仅当有**足够质量的领域标注**、且**提示工程已到上限**时才考虑；蒸馏把大模型压到自托管小模型。

**判据：先问「瓶颈是知识还是能力」。** 没资料→补语料与检索；有资料答不好→轮到微调与 Agent。

## 20.6 复盘与交接：把隐性知识变成资产

交接是**把判断力给你**，不是给代码。清单：runbook、演练记录与三类回滚计时（m19）、运营机制（20.3）、评测集与门禁用法（m14）、「**已知的坑**」。**下个团队照它能否半天内处置一次故障？**

## 20.7 完整链路图：从立项到运营

```text
[立项] 目标/代价分级/SLO            (m01)
   ▼
[建模] 元数据·权限·切分前置决策      (m02)
   ▼
[数据与索引] 接入→解析→切分→向量化   (m03–m06)   ▲ 索引=制品②
   ▼
[检索质量] 基线→混合重排→查询理解    (m07–m09)
   ▼
[生成与可信] 拼装/拒答·引用溯源      (m10–m12)
   ▼
[评测体系] 黄金集·回归门禁·在线闭环   (m13–m15)
   ▼
[平台化] 多租户·服务化·可观测成本     (m16–m18)
   ▼
[上线发布] 四元组制品·金丝雀·回滚     (m19)      ▲ 模型=制品①
   ▼
[运营与演进] 压测·演练·运营·成本·演进  (m20)  ◄── 你在这里
```

**最脆弱的一环通常是[运营与演进]及其依赖的[评测体系]。** 三个理由：

1. **它是唯一「上线后没人再投入」的环节**：[立项]–[上线]都在反复执行，运营只在出事时才被想起。
2. **它依赖「评测集仍代表真实问题」**：运营决策全凭评测集判据，问题漂移而评测集没跟上，会**自信地优化错方向**。
3. **它跨越最多边界**：源站、权限、推理、向量库、成本；任一处无人负责，都在「最需要它的那次」暴露。

**加固顺序**：① 运营机制**有人负责**；② 评测集**对齐真实问题**；③ 最后才谈**演进**。

## 20.8 差距清单与收束

**先补信任根，再补便利**：

| 能力 | 现状 | 目标 | 优先级 | 依赖 |
|---|---|---|---|---|
| 四元组制品版本化可追溯 | | | 高 | 制品库/命名规范 |
| 三类回滚分别演练并计时 | | | 高 | 索引快照/别名 |
| 评测集回归门禁 | | | 高 | m13 黄金集 |
| 容量拐点已知 | | | 高 | 分层压测 |
| 内容运营机制（owner/过期/缺口） | | | 中 | 元数据 last_verified |
| 分阶段成本优化 | | | 中 | 缓存/观测 |
| 演习常态化（故障注入） | | | 中 | runbook |
| 演进（多模态/Agent/微调） | | | 低 | 前三项全绿 |

**可验证性优先于能力扩展**：四元组可追溯、回滚可演练、评测可回归、容量已知是信任根，否则演进只是更快更贵地犯错。

**二十个里程碑收束**：主线同一条——**让每步可验收、每次变更可回退、每个决策有数据依据**。
