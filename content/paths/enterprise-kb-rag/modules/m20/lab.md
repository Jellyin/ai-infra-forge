# 🧪 动手实验 · 里程碑 20

> **本里程碑的交付物**：① 容量压测报告（含拐点与瓶颈分层结论） ② 故障演练记录（含至少一条改进项） ③ 内容运营机制草案 ④ 分阶段成本优化路线 ⑤ 交接清单。

## 档位 A · 真实项目（把运营变成有 owner 的机制）

## 档位 B · 本地（kind：压测 + 故障注入 → 观测 → 回滚）

目标：把「**发现坏 → 判定 → 止血**」闭环走一遍，并找出一个小集群的容量拐点。m19 已练过「发布→观测→回滚」，本档位推进到**压测与注入**。

```bash
kind create cluster --name ops-rehearse
# metrics-server 便于观察资源（kind 默认不含；安装方式以官方文档为准）
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
kubectl create deployment web --image=nginx:1.25 --replicas=2
kubectl rollout status deployment/web
```

### 1. 找拐点（哪怕只是玩具服务）

```bash
# 最小压测工具任选（hey/ab/vegeta）；以 hey 为例
hey -z 30s -c 10 "http://$(kubectl get svc web -o jsonpath='{.spec.clusterIP}')"
hey -z 30s -c 50 "http://$(kubectl get svc web -o jsonpath='{.spec.clusterIP}')"
kubectl top nodes
```

| 并发 | p95 | 结论 |
|---|---|---|
| 10 | | |
| 50 | | |
| **拐点** | | p95 从这一档开始非线性上升 |

> 关键习惯：**先预热再计时、每档跑够时长、固定变量**。只跑一次、只看平均值的压测结论不可信。

### 2. 故障注入 → 观测 → 回滚

```bash
kubectl delete pod -l app=web              # 注入：杀一个 pod，验证副本下限与自愈
kubectl get pods -l app=web -w             # 观测：副本是否被拉回（Ctrl-C 退出）

kubectl set image deployment/web nginx=nginx:does-not-exist   # 制造坏发布
kubectl describe pod -l app=web | tail -20
time kubectl rollout undo deployment/web   # 走一次回滚并计时
kubectl rollout status deployment/web
```

| 你的观察 | 结论 |
|---|---|
| 单 pod 被删后副本自动拉回 | 自愈生效，但要问：**指标有没有发现它**？ |
| 坏发布是否被自动判定 | 本地无门禁时靠人；这正是探针/门禁要补的地方 |
| 回滚耗时 | 这是你的**本地 MTTR 基线** |

### 3. 写成脚本，沉淀为 runbook

```bash
cat > drill.sh <<'SH'
#!/usr/bin/env bash
set -euo pipefail
echo "== 注入：删一个 pod =="; kubectl delete pod -l app=web; sleep 10
echo "== 观测：副本状态 =="; kubectl get pods -l app=web
echo "== 结论：自愈是否生效？指标能否发现？ =="
SH
chmod +x drill.sh && ./drill.sh
```

> 把每一步写进 runbook（命令 + 耗时 + 判据），这就是可交接的资产。

## 档位 C · 纸上评审（40 分钟）

读下面这条**按时间顺序的故障时间线**，回答两问：**止血顺序**（第一步动什么、为什么）与**影响面**（谁受影响、多久、能否更早发现）。

```text
周五 14:00  上游 wiki 改版，页面 URL 结构变化（源站变更，未通知知识库团队）
14:20  增量接入任务开始失败，但失败只写进日志，无告警
18:00  值班发现“最近两小时问题命中率下降”，归因为“没什么人问”
周夜  接入持续失败，新页面完全没进索引（旧页面仍在）
周六 09:00  业务方投诉：“新发布的制度文件搜不到”
09:10  值班判断是接入问题，重跑全量接入（预计 6 小时）
09:20  全量重跑再次失败——URL 结构变了，解析规则不匹配
15:30  修改解析规则后重跑成功，命中率恢复
```

<details><summary>对照答案（先写完再看）</summary>

**止血顺序错了**：**第一步就动错了——重跑全量接入不是止血，是扩大影响**。正确顺序：

1. **先判影响面**（哪些源/租户受影响、是「新增缺失」还是「全量损坏」）。本例旧页面仍在，属**增量缺失**，可控，不需全量重跑。
2. **先修解析规则，再小范围回填**，而非「先重跑全量」。09:10 直接重跑，09:20 又失败，白等且风险更大。
3. 最快止血可能是**先让失败可见**（加告警）并把「新制度文件」这类高价值源**手工优先接入**，而非等 6 小时全量。

**影响面**：真实影响从 **14:20 到 15:30**，约 **25 小时**。暴露被拉长，根因有三：① **失败无告警**——接入失败必须可见且会告警；② **源站变更无契约**（上游改 URL 不通知）——需结构变更监测或定期探活；③ **归因错误**（把命中率下降归为「没人问」）——命中率是 SLI，下降就该查。

**根因**：「源站变更」这类故障没进演练清单、也没监测——这正是 guide 20.2 把它列为必演场景的原因。

</details>

### 最后一问

这次最贵的是 **25 小时静默失效**，而不是某台机器坏了。若只能加一条防线，你加在**监测**（接入失败/源站变更告警）、**运营**（高价值源有 owner 优先保障）、还是**演练**（源站变更纳入常态化注入）？写下理由。
