# 里程碑 9 · 查询理解：改写、多跳与元数据过滤

> **本里程碑的交付物**：查询改写模块（可独立开关）、多跳问题的拆解流程、自然语言意图→元数据过滤条件的映射表、以及每个增强模块的开关清单与评测归因记录。
> **验收标准**：任意同事能逐项开关每个增强、并说出它单开时对 recall 与 precision 的净影响——包括「某增强开了反而变差」，这个负结论同样是有价值的交付物。

## 9.1 用户的问题不是检索式的

用户输入的是「上次那个报错到底咋回事啊」，而索引里躺着的是「错误码 `0xE003`：连接池耗尽」。**问题与文档之间存在一条沟**：口语化、指代不明、缺实体、意图藏在字面之外。查询理解就是填这条沟——但**每填一步都可能填错**，所以本模块的核心不是「加什么」，而是「加了之后怎么证明没害处」。

## 9.2 查询改写与扩展

三类动作要分清：**同义**（AK→Access Key）、**去口语化**（去掉「咋回事」）、**补全指代**（「上次那个」→补上具体实体，需会话上下文）。

提示词骨架（要点是**约束它别乱加实体**、并输出可归因的结构）：

```text
你是检索查询改写器。把用户的口语提问改写成适合检索的关键词查询。
规则：
1. 只补全指代与省略，不引入用户没提过的实体。
2. 编号、版本号、专有名词（M4、v2.3、AK、0xE003）保持原始写法，不做同义替换。
3. 输出 JSON：{"rewritten": "...", "added_terms": ["..."], "dropped": ["..."], "confidence": 0.x}
   若无法确定指代，added_terms 留空并把 confidence 调低。
```

**`added_terms` 与 `dropped` 是给评测用的**：它们让「这次改写动了什么」变得可审计，而不是一个黑盒的新 query。

## 9.3 多跳拆解：先检索什么、再检索什么

多跳问题的特征是**第二步的检索依赖第一步的结果**，不能一次检索解掉，要显式拆成有顺序的子查询。

```text
Q: 「M4 评审里定的超时阈值，现在最新的配置里是多少？」

hop1（找锚点）：检索「M4 评审 超时阈值」──► 得到阈值 X 与它当时的版本号
hop2（验证现状）：检索「超时 配置」+ 元数据过滤 version >= 当前版本 ──► 得到现值 Y
synthesize：对比 X 与 Y，回答「是否变更、现值为多少」
```

工程要点：**每跳都要能被单独评测**（分别记 hop1/hop2 的 recall，才知道哪一跳在拖后腿）；**设跳数上限**（如 3，超出就拒答或转人工——多跳容错最低，无限拆解会把错误累加）；只对标注为「多跳」的题开这条路径（见 9.6）。

## 9.4 意图识别与元数据过滤：把「我们部门的」变成过滤条件

很多「检索不准」其实是**检索范围错了**——本该只在本部门文档里搜，却在全库搜。意图识别的产出不是一段文字，而是一组**过滤条件**：

| 自然语言线索 | 意图 | 落到什么过滤条件 |
|---|---|---|
| 「我们部门的」 | 范围 | `dept = <当前用户所属 dept>`（由身份推导，不是用户说了算） |
| 「最新的」 | 时间/版本 | `version = max` 或 `updated_at >= T-90d` |
| 「去年的」「Q3 的」 | 时间 | `updated_at ∈ [区间]` |
| 「正式的/对外版」 | 文档类型 | `doc_type = 'official'` |
| 「上次那个报错」 | 指代 | 需求助会话上下文改写，**不能**凭空编造过滤值 |

**关键判断**：「我们部门的」这类范围意图，过滤值应当**取自用户身份**（服务端推导），绝不能让模型或用户自由指定——否则就是一个越权漏洞。过滤在**检索前**生效，先缩小范围再算相似度。

## 9.5 时间与版本意图：「最新」要落到版本字段

「最新」是查询理解里最常见也最容易错的一类。它不是普通词，而是**必须落到结构化字段**的操作：取 `version = max`、按 `updated_at` 排序取最近、或限定时间窗。若只把它当普通词丢进检索，BM25 会去匹配字面「最新」二字，向量会去匹配「新」的语义——两者都答不对。**凡涉及时间/版本的词，都要先翻译成过滤或排序，再进入检索。**

## 9.6 每个增强都要可独立开关并归因

这是本模块的方法论核心。把每次查询理解的动作做成**独立可开关的模块**，才能知道是哪个在起作用：

| 增强 | 开关 | 默认 | 归因方法 |
|---|---|---|---|
| 查询改写 | `rewrite.enabled` | off | A/B 比 recall@10 |
| 同义/词典扩展 | `expand.synonyms` | off | 词典命中率 + recall 增量 |
| 元数据过滤 | `filter.enabled` | **on** | 过滤前后 precision；越权红队用例 |
| 多跳拆解 | `multihop.enabled` | off | 仅对标注为多跳的题开启并单独评测 |
| 时间/版本意图 | `temporal.enabled` | on | 「最新」类题的答案正确率 |

**归因纪律**：一次只开一个开关，跑同一黄金集，记录 before/after。若两个增强同时上线，你无法判断收益来自哪一个——这就是「可开关」的工程价值。

## 9.7 过度改写会引入漂移：要能量化它的代价

改写可能把原问题**改到另一个意思**上去，这就是语义漂移。三个可量的信号：

```python
# 每次改写都记一条，攒起来做分布看
drift = 1 - cosine( embed(original_query), embed(rewritten_query) )
# 低于阈值（如 cosine < 0.8）→ 标记为「疑似漂移」，进人工抽检队列
```

1. **改写前后 query 的 embedding 余弦距离**——越大越可能跑偏。
2. **黄金集上 recall 与 precision 的 delta**——若 recall 升但 precision 降，说明改写引入了无关词把噪声也拉进来了。
3. **`added_terms` 中不在领域词典里的比例**——模型越爱自由发挥，这个比例越高，越危险。

**负结论也是交付物**：若某增强在这些指标下净收益为负，就默认关掉它，并把「开了会变差」写进记录。这比强行保留一个「看起来聪明」的模块更有价值。

## 9.8 本里程碑的判断力

- 有人要「加个查询改写提效果」时，先要：**改写的 A/B recall 数字，以及漂移阈值命中率**。
- 看到「最新」出现在查询里，先问：**它被翻译成 version / updated_at 过滤了吗？** 没有就是 bug。
- 看到「我们部门的」，先问：**过滤值是身份推导的还是模型生成的？** 后者是越权风险。
- 任何增强上线前，先确认它**能单独关掉**——关不掉的增强，将来也定位不了问题。
