# Day 21 · 生产就绪与结课演练

## 21.1 上线检查单：从清单化到可自动校验

大多数团队的上线检查单是一张写死在 wiki 里的表，靠「自觉」勾选——它最大的问题是**不会失败**。真正有价值的是把它拆成三类：能自动校验的、能自动告警的、只能人判断的。

| 检查项 | 类型 | 校验方式 |
|---|---|---|
| 制品已签名且可验签 | 自动 | `cosign verify` 非空返回 |
| SBOM 已生成并归档 | 自动 | 制品仓库中存在对应 digest 的 SBOM |
| 镜像 digest 与部署清单一致 | 自动 | 比对流水线产出 digest 与 Git 中的 manifest |
| 错误预算充足（burn rate ≤ 1） | 自动 | Day 20 的 `check-error-budget` |
| 回滚路径已演练 | 半自动 | 演练记录存在 + 目标 revision 可解析 |
| 容量有余量（p95 < 阈值） | 半自动 | 观测查询 |
| Runbook / oncall 已就位 | 人判断 | 评审 |
| 变更影响与数据迁移可逆性 | 人判断 | 评审 |

**原则**：凡是能用机器判定的，就别放进「勾选表」——勾选表只留下真正需要人判断的少数几项。一张 90% 靠人勾的检查单，迟早会变成 90% 靠人跳过。

## 21.2 容量与成本进入发布流程

容量和成本不是运维的季度报告，而是**发布时的输入**：

- **容量**：声明 `requests`/`limits`、确认 HPA 目标与副本下限、留出突发余量（headroom）。门禁判据：部署后预估 p95 是否逼近限流/饱和阈值。
- **成本**：把「每次请求成本」「每月单副本成本」做成随服务走的指标，按标签/团队分摊。门禁不是「禁止花钱」，而是让「这次发布会不会让单位成本翻倍」在发布前可见。
- **回归**：把容量与成本纳入 SLO 看板的同一行，让增长趋势在发布节奏里被看见，而不是季度才发现。

## 21.3 回滚演练与故障注入：练成肌肉记忆

**回滚不是「需要时再做」的动作，是需要每周演练的技能。** 没演练过的回滚，等于没有回滚。

```bash
# 蓝绿/滚动：回退 Deployment 到上一版（或指定 revision）
kubectl rollout history deployment/payments-api
kubectl rollout undo deployment/payments-api --to-revision=3
kubectl rollout status deployment/payments-api

# Argo Rollouts（需安装 kubectl argo rollouts 插件）
kubectl argo rollouts get rollout payments-api
kubectl argo rollouts undo rollout/payments-api

# GitOps：回退到某个已同步的历史 revision
argocd app history payments-api
argocd app rollback payments-api <REVISION>
```

**演练成功标准**（缺一不可）：① 从「决定回滚」到「用户恢复」的时长有上限（如 ≤ 5 分钟）；② 数据一致性成立（迁移是否可逆）；③ 告警/错误预算曲线确实回落；④ 结论进入 runbook。

**故障注入**（chaos）：杀掉一个 pod、注入 300ms 网络延迟、掐断一个下游依赖、把某个实例 CPU 打满——目的是**验证「指标能否发现它」以及「自动/人工回滚是否会触发」**，而不只是验证「服务没挂」。

## 21.4 端到端图：一条从提交到生产的完整链路

```
 commit / MR
   │
   ▼
 [1] 检查/测试           lint · unit · 契约 · e2e（分层，Day 2）
   │
   ▼
 [2] 多架构制品 + 签名   amd64/arm64 镜像 · SBOM · cosign 签名（Day 6/7/9）
   │
   ▼
 [3] 供应链门禁          漏洞/许可证/策略准入 · 验签（Day 4/9）
   │
   ▼
 [4] GitOps              更新清单仓库 → ArgoCD 同步（Git 是唯一事实源，Day 12）
   │
   ▼
 [5] 渐进式发布          Argo Rollouts canary：指标判定，达标才全量（Day 14）
   │
   ▼
 [6] 观测与回滚          OTel/SLO · burn rate 门禁 · 自动或人工回滚（Day 20）
```

这条链的每一段都对应着一到两天的内容。它的价值不在画得好看，而在于**每段都有机器可验证的契约**：签名可验、GitOps 有 diff、canary 有指标阈值、门禁会 fail。

## 21.5 这张图里最脆弱的一环通常是哪个，为什么

多数人会指 [2] 供应链或 [5] 渐进式发布——它们名字最唬人。**但真正的弱环通常是 [6] 的回滚路径，以及它所依赖的观测信号是否可信。**

理由有三条，且都反直觉：

1. **它是唯一「没人真的点过」的环节**。[1]–[5] 每条都在每次发布中被反复执行；回滚只在出事时才用——**用得最少、坏得最隐**。一个从没演练过的回滚命令，很可能在真出事时因权限、revision 不可解析、或数据迁移不可逆而当场失败。
2. **它依赖「指标是对的」这个前提**。canary 的自动回滚、burn rate 门禁，前提是 SLI 与指标可信。若 `service.version` 打错、指标口径不一致（Day 20），系统会**自信地做错决定**——该回滚时判定「一切正常」。
3. **它跨了最多系统边界**：部署系统、Git、制品仓库、观测、凭证。任何一处长期凭证/权限过期，都会在「最需要它的一次」暴露。

**加固顺序**：先**定期回滚演练**（练成肌肉记忆），再让**观测信号可信**（`service.version` 对齐发布、口径统一），最后才把回滚做成**自动门禁**。跳过前两步直接自动化，只会把「自信地做错」自动化。

## 21.6 把这次发布沉淀为可复用资产

每一次发布都应该是下一次的模板。沉淀清单：

- 把本次的流水线抽成**带版本的 component**（Day 19）；
- 把检查单里「可自动」的项变成**会 fail 的 job**，而不是文档；
- 把 runbook、回滚步骤、演练记录**写进仓库**（随代码走）；
- 把 SLO 与看板**代码化**（版本化管理，而非手点）；
- 把复盘行动项**纳入统一 issue 追踪**并标注 owner/截止日。

判据：**下一个团队照你留下的东西，能否在半天内复现同一条链路？** 不能，就只是一次发布。

## 21.7 差距清单：现状 vs 目标，补齐顺序

给自己项目打一张表，**先补信任根，再补便利**：

| 能力 | 现状 | 目标 | 优先级 | 依赖 |
|---|---|---|---|---|
| 制品不可变 + 签名验签 | | | 高 | 制品仓库 |
| 供应链门禁 | | | 高 | 签名 |
| 「假绿灯」清零（Day 1/2） | | | 高 | 测试分层 |
| 错误预算门禁 | | | 中 | 可观测 |
| 渐进式发布 + 自动回滚 | | | 中 | GitOps |
| 模板组件化与版本化 | | | 中 | — |
| 回滚演练常态化 | 必做 | | 高 | 观测信号可信 |

**排序原则**：可验证性（签名、门禁、假绿灯）优先于便利性（自助、门户）。因为前者是**信任根**——没有它，后面的自动化只是在更快的速度上犯错。

## 21.8 二十天收束

从 Day 1 的「假绿灯」到今天的端到端图，你要走的是同一条主线：**让每一步都可验证，让每次发布都可回退。** 剩下的不是学新工具，而是把这二十天在你自己的项目里补成一张 21.7 的表，按优先级一个个填。
