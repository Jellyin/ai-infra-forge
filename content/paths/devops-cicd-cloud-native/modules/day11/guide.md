# Day 11 · 环境模型与晋升策略

## 11.1 把「环境」当成一套职责，而不是几台机器

「我们有 dev、staging、prod」是不完整的描述。真正要回答的是：**这个环境为谁负责什么、坏了谁受影响、允许多快变更**。用职责而非机器定义环境，矩阵才立得住。

| 环境 | 为谁负责 | 数据 | 变更自由度 | 生命周期 |
|---|---|---|---|---|
| **dev** | 开发者自测 | 假数据，可重建 | 随时、可破坏 | 长驻，可重置 |
| **review** | 每个 MR 的验收者 | 假数据，按 MR 隔离 | 随 MR 更新 | **与 MR 同生命周期，合并/关闭即销毁** |
| **staging** | 发布前回归与验收 | 仿生产（脱敏） | 受控，需通过测试 | 长驻、稳定 |
| **prod** | 真实用户 | 真实数据 | 最慢，需审批与窗口 | 长驻，受 SLO 约束 |

三条判断力：**review** 证明环境可以「随变更生、随变更灭」，不必是长驻机器；**staging 存在的唯一理由是「与 prod 同构」**，配置/依赖/拓扑不一致只会带来虚假信心；**环境越多成本越非线性**，每个都要独立的数据、凭证、网络与维护，矩阵要能画出「谁晋升到谁」。

## 11.2 分支策略：trunk-based 与 Git 分支流的真实成本

环境数量与分支策略绑死——**每多一条长命分支，就多一个要维护的目标**。

| 维度 | trunk-based | Git Flow 式分支流 |
|---|---|---|
| 分支寿命 | 小时级，直合主干 | 天到周：develop/release/hotfix/feature |
| 集成时机 | 持续集成，天天合 | 发布前集中合并 |
| 合并冲突 | 小、局部 | 大、跨分支，越晚越痛 |
| 环境映射 | 主干 → 环境，feature flag 控开关 | 分支 → 环境，一分支一环境 |
| CI 负载 | 分支少，重复少 | 分支多，同一提交重复跑 |
| 对工程的要求 | 高：自动化测试 + 特性开关 + 快速回滚 | 低：靠流程与人工把关 |
| 典型失败 | flag 腐烂、开关组合爆炸 | merge hell、集成回归集中爆发 |

`release` 这类长命分支的真实成本是**集成被推迟到最后一刻**：所有分支在发布前同时汇合，冲突与回归一起爆发，而你此时最没时间。trunk-based 不是「不要分支」，而是**让分支短命**，用 feature flag 把「代码合并」与「功能发布」解耦。

> 选择题不是「哪个更好」，而是「你的自动化与回滚能力撑不撑得起短分支」。撑不起，先补测试与回滚。

## 11.3 GitLab environments 与 GitHub Actions environments 对照

| 能力 | GitLab CI | GitHub Actions |
|---|---|---|
| 环境声明位置 | CI 配置里（job 的 `environment:`） | 仓库设置里定义，job 用 `environment:` 引用 |
| 动态 URL / 预览 | `environment.url`，可在 job 里生成 | environment 的 `url` 输出 |
| 临时环境自动销毁 | `environment:on_stop` + stop job | 依靠 workflow 自行清理 |
| 受保护环境 | Protected Environments（限制谁能部署） | environment protection rules |
| 部署审批 | 受保护环境上的部署审批（部分能力与订阅层级相关，**以官方文档为准**） | required reviewers / wait timer |
| 允许部署的分支 | 受保护分支 + 环境规则 | environment 限定可部署的 branch / tag |

`on_stop` 是做 review app 的关键：定义一个「停止」job，环境随 MR 关闭自动清理，否则临时环境会变成僵尸。

## 11.4 手动门禁与审批：责任交接，而不是多打一次勾

```yaml
# GitLab：手动 job + 受保护环境
deploy:prod:
  stage: deploy
  environment:
    name: prod
    url: https://app.example.com
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      when: manual        # 人工闸门；无人点击则永不部署
  script:
    - ./bump-image-digest.sh   # CI 只改声明，不碰集群（Day 12 展开）
```

- **手动 job（`when: manual`）**：把执行变成显式动作，但**不提供审批语义**——谁点的、依据什么，平台不管。
- **受保护分支**保护**代码入口**（谁能 push/合并）；**受保护环境**保护**部署入口**（谁能部署、谁可批准）。两者不能互相替代。
- **审批（approval）**的真正价值是**责任交接**：把「谁在什么时点批准了这次发布」变成可追责记录。

> `when: manual` 的隐藏失败模式：没人点，流水线依然绿，环境却停在旧版本——Day 1 的假绿灯在 CD 阶段重演。

## 11.5 环境隔离的最小集：数据、凭证、网络

隔离的目的不是「干净」，而是**让一次错误无法跨环境扩散**。

- **数据**：每环境独立库/schema，**绝不共享 prod 数据库**；staging 用**脱敏**快照而非 prod 直连；迁移脚本幂等、可重放、先在不重要环境验证。
- **凭证**：每环境一套独立凭证，**prod 凭证只对 prod 生效**；K8s 上最小隔离单元是 **namespace + 独立 ServiceAccount + RBAC**；能用 OIDC/Workload Identity 换取的，就不要下发 kubeconfig。
- **网络**：环境落在不同 namespace/VPC/subnet，**默认拒绝**（NetworkPolicy）按需放行；prod 不与 dev 互通。

> 一句话：**命名空间隔离是下限，数据与凭证隔离才是防线**。三环境共用一套数据库凭证，等于没有隔离。

## 11.6 回滚窗口与「不可回滚变更」

**回滚窗口** = 从变更上线，到「还能安全回滚」这段时间。它是**约束的边界**，不是技术问题。

- 窗口为什么会关闭？① schema 已改；② 数据已被新逻辑写入；③ 外部 API/契约已发布；④ 已有下游消费了你发出的事件。
- **能回滚的**：无状态服务的镜像版本回退（把 Git 里的 digest 指回旧值，ArgoCD 自动收敛）。
- **不能/难回滚的（要单独识别）**：破坏性 schema 变更（`DROP COLUMN`）、数据迁移、对外契约变更、已发事件、密钥轮换。

**处置方针：把不可回滚变更拆成可回滚的步骤（expand / contract）**：① **Expand** 先加新列、保持兼容；② **Migrate** 双写/回填；③ **Switch** 切读路径并观察；④ **Contract** 确认无误才删旧列。每步单独可回滚，窗口被拆散；配合 feature flag 比「重部署旧版本」更快。

> 提醒：ArgoCD 的 `rollback` 只能把**声明**退回旧版本，**退不了数据**。凡动了数据的变更，回滚方案必须在变更前写好。

## 11.7 今天要建立的判断力

- 看到「我们有三个环境」，先问：**每个为谁负责、晋升路径是什么**。
- 看到长命分支，先问：**它对应哪个环境？成本谁付**。
- 看到「加一道审批」，先问：**它拦的是代码入口还是部署入口，追责到人了吗**。
- 看到一次变更，先问：**它的回滚窗口有多长，有没有不可回滚的部分**。
